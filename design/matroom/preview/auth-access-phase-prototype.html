Observed common structure (written after building the four sections above — not decided beforehand)

All four scenarios land on the same shape: a centered, max-width card (380-420px), the wordmark at the top, an `h1`, an optional one-line `.sub`, then either a form, a list, or a single state icon + message, then one primary action and (usually) one link-style secondary action. That repetition is real, not assumed — it is the same shell with different middles.

What is not identical: the organization-selection card needs a wider max-width (420px vs 380px) to fit a row's name/role pair without wrapping awkwardly, and its content is a list, not a form or a message — meaningfully different internals, not just a styling variant.

  • Justified as one shared component: the outer card shell (centering, max-width, card background/border/radius, the wordmark block, the heading+sub pattern). This is genuinely identical across all four and is where a real "AuthCard" component should start.
  • Not justified as part of that same component: the form-field group, the org-list group, and the single-state-icon group are each their own small, separate piece — composed inside the shared card shell, not folded into one giant configurable component. Building three small pieces plus one shared shell is more honest than one component with a dozen conditional props.
  • Still open: whether the access-denied pattern (section D) should be ONE component parameterized by icon/message/action, or three separate near-identical pages — the three real screens' exact copy needs to be read before deciding; this prototype used placeholder copy only.

Recommendation: approve the shell shape shown above; defer the exact component boundary (one shell + three small pieces, as sketched) to implementation, where real code can confirm it holds once the actual existing screens' real copy and logic are read against it.
