## 1. Overview

The dues ledger tracks what a student owes an academy (branch) for tuition, on a monthly or multi-month basis, and how that debt is settled — replacing the legacy `PaymentPeriod` model's single `status` column (`PAID`/`PENDING`/`PROMO`/`EXEMPT`, no due date, no grace, no fee, no partial payment, no exchange rate) with an append-only ledger of obligations, fees, payments and settlements. The legacy model and every legacy payment record are completely untouched — nothing in this feature reads or writes `PaymentPeriod` (`PROPOSAL.md` §B1/§B10), and no organization's real billing behavior has changed as a result of any of it (§7, "Inactive billing gates").

**Core entities** (`prisma/schema.prisma`):

- **`DuesPolicyVersion`** — a branch's due day, grace day, late-fee amount/currency and prepayment-months limit, versioned by effective month. One row per branch per effective month.
- **`PaymentPlanTerms`** — a plan's price, currency and months-covered, versioned by effective month. `monthsCovered = 1` is an ordinary monthly plan; `>= 2` is a multi-month package (`DuesObligation_shape_by_type`, `20260927153000_dues_ledger_schema/migration.sql:246`, enforces this exactly — `>= 2`, not `>= 1` more).
- **`StudentPlanAssignment`** — which plan a student is on, effective from a given month. `planId: null` is a first-class "explicitly unassigned" value, distinct from "no row yet" (undecided).
- **`StudentStatusChange`** — an append-only history of a student's status (`ACTIVE`/`INACTIVE`/`PENDING`/`ARCHIVED`), the fact the eligibility function reads instead of trusting `Student.status`'s current value for a past month.
- **`DuesObligation`** — one row of debt: `MONTHLY` (recurring tuition for one coverage month), or `PACKAGE` (one multi-month offer, its own price, never late, never partial). Whole-row immutable, including its dates (`prisma/migrations/20260927153000_dues_ledger_schema`'s trigger).
- **`DuesCoverage`** — one row per calendar month an obligation reserves; unconditionally unique per student per month across every obligation type, so a `MONTHLY`, a `PACKAGE`, and any future overlap are all prevented by the same constraint.
- **`DuesLateFee`** — a marker (not a separate amount; the fee is the obligation's own snapshotted `lateFeeAmount`) that a `MONTHLY` obligation is overdue, unique per obligation, with a generic removal marker (`WAIVED` or `VOIDED`) that is complete-or-null and one-time at the database level.
- **`DuesPayment`** / **`DuesSettlement`** — an immutable payment record and the link from a payment to the obligation(s) it settles. New settlement rows are only ever inserted, never edited or deleted; a reversal does not remove or replace a settlement row, it sets that same row's own reversal marker (below). At most one **active** (unreversed) settlement may exist per obligation at a time (`DuesSettlement`'s partial unique index, `WHERE reversedAt IS NULL`) — a reversed settlement remains in the table as history, and a later payment for the same obligation inserts a new, second settlement row.
- **`ExchangeRateQuote`** — an owner-entered BCR USD sell rate for a specific date, append-only, corrected only by a new, explicitly-numbered `revision` (never an edit), added in the currency-conversion work (§3).

**The "narrow transaction-aware extraction" pattern**, used repeatedly across this feature rather than duplicated or reinvented each time a new writer needs an existing writer's core logic: a public function (e.g. `createMonthlyObligation`, `recordDuesPayment`) opens its own transaction and does its own pre-transaction checks, then delegates to an exported `*InTx` sibling (e.g. `createMonthlyObligationInTx`, `recordDuesPaymentInTx`) that takes an already-open `tx` and does the real work, trusting nothing from its caller — re-checking scope, activation and role itself rather than assuming a caller already did. This is what let `prepayMonthlyObligations` and `purchasePackage` reuse `recordDuesPaymentInTx`'s settlement core, and `correctLateFeeAndSettle` compose the fee-void and the settlement in one transaction, without ever nesting a `prisma.$transaction` inside another (the exact mistake identified and reverted once, in the eligibility-prerequisites work — see `docs/dues/history/ELIGIBILITY-PREREQUISITES-BRIEF.md` §3.4).

**Lock order**, fixed and shared by every writer that touches more than one row: branch (`FOR SHARE` for a ledger writer, `FOR UPDATE` for a configuration correction) → student (`FOR UPDATE`) → terms/policy/assignment (`FOR SHARE` for a ledger writer, `FOR UPDATE` for a correction). This is the order `create-monthly-obligation.ts` established first, and each writer below was specifically traced against it in its own brief, not assumed to follow it automatically: `assignPlan` was found to take no student lock at all and was given one, in this exact position, to close two real assignment races (`docs/dues/history/MONTHLY-GENERATION-BRIEF.md` §5); `prepayMonthlyObligations` and `purchasePackage` added `lockAssignmentShared` at the terms/policy step for the same reason (`docs/dues/history/MONTHLY-PREPAYMENT-BRIEF.md` §5); `correctLateFeeAndSettle`, `reversePayment`, and `waiveLateFee` take only the student lock, since none of them resolves a terms/policy/assignment version. This is the specific set of writers verified against this order — not a claim that every present or future writer in this codebase has been checked for it.

## 2. Ledger invariants

- **Money facts are never deleted, and a new financial fact is always a new row.** No writer deletes a `DuesObligation`, `DuesPayment`, or `DuesSettlement` row, and a correction never invents a substitute value in place of an existing one's own fields — a new payment, a new settlement, or a new `ExchangeRateQuote` revision is always a new, inserted row. **Reversal and removal are the one exception to "always a new row," and are worth stating precisely rather than folding into the same sentence**: voiding or waiving a `DuesLateFee`, and reversing a `DuesPayment`/`DuesSettlement`, each work by setting that *same, already-existing* row's own nullable marker fields exactly once (below) — not by inserting a new marker row. The row being marked is not new; only what happens *after* the mark (a later payment inserting a genuinely new settlement row, for instance) creates new rows.
- **Whole-row immutability where it matters.** `DuesObligation`'s entire row, including its due/grace dates, is immutable at the database level (`DuesObligation`'s trigger, `20260927153000_dues_ledger_schema`) — rescheduling has no approved policy, so the database gives it no exception.
- **One-time removal/reversal markers, complete or null, enforced by Postgres, not application discipline.** `DuesLateFee`'s `removedAt`/`removalKind`/`removedById`/`removalReason` and `DuesPayment`/`DuesSettlement`'s `reversedAt`/`reversedById`/`reversalReason` are nullable fields on those tables' own existing rows (not a separate table or a new row), each guarded by a `..._marker_complete` CHECK constraint (all four fields null, or all four set with a non-blank reason) and a `dues_set_once_marker` trigger that rejects any further change once set — a second void, waiver, or reversal attempt is refused by the database itself, independent of whether application code happens to check first.
- **Authorization is writer-by-writer, not a blanket policy — verified directly against each writer's own code, not assumed from a pattern.** `waiveLateFee`, `enterExchangeRateQuote`, `reversePayment`, `purchasePackage`, `prepayMonthlyObligations`, and `correctLateFeeAndSettle` each check `context.organizationRole !== "ADMIN"` themselves and refuse otherwise (owner-only, by explicit, confirmed design in each one's own brief). **`recordDuesPayment` has no role check of any kind** (grepped `record-payment.ts`: zero matches for `organizationRole`) — this is not an oversight, it is D5 below, explicitly still open ("who besides owners may record ordinary payments" — `docs/dues/history/LEDGER-WRITERS-BRIEF.md` §4: *"Who may call: the functions do no role check; the eventual action does"*). None of this is authorization in the request-handling sense yet regardless of which writers check a role today: no writer is reachable from any route or action (§6), so "owner-only" here means "this function's own internal check," not "only an owner can currently trigger real billing" — nobody can, from outside a test, at all.
- **`MAX(x)+1`-under-lock, never a wall-clock timestamp, for anything that needs same-instant ordering.** `StudentStatusChange.sequence` (assigned as `MAX(sequence)+1` under `lockStudent`, `docs/dues/history/ELIGIBILITY-PREREQUISITES-BRIEF.md` §3.2) and `ExchangeRateQuote.revision` (assigned as `MAX(revision)+1` under the exchange-rate advisory lock, §3 below) both exist because a transaction-start timestamp (`createdAt`) cannot reliably reflect true commit order under lock contention — a transaction that began later but queued less can commit first, with an earlier `createdAt` than a transaction that began first but waited longer. This was corrected once during design (the eligibility-prerequisites brief's own revision history) and the lesson was reused deliberately for `ExchangeRateQuote.revision` rather than repeated.
- **DB-level CHECK constraints encode type-specific shape, not just application validation.** `DuesObligation_shape_by_type` requires a `MONTHLY` row to have `monthsCovered = 1` plus `dueOn`/`graceDeadline`/`lateFeeAmount`/`policyVersionId` all set, and a `PACKAGE` row to have `monthsCovered >= 2` with all four of those fields NULL — making "a package is never late" a structural fact, not a convention an application writer could forget.
- **Composite tenant FKs everywhere.** Every dues table carries `organizationId`, with `(organizationId, id)` composite foreign keys throughout, registered in both `tenant-guard.ts`'s and `scoped-client.ts`'s `TENANT_SCOPED_MODELS` (kept in sync by a test) — including `ExchangeRateQuote`, which was briefly missing from both until caught during PR #78's own review and fixed before merge.
- **Two separate guarantees, not one — worth keeping distinct.** `DuesCoverage`'s `(studentId, year, month)` uniqueness (unconditional, not scoped by obligation type) is what makes **no overlap** structural: a package's N coverage rows collide with the exact same database constraint an ordinary monthly obligation's single row would, and a reversal never releases coverage (deliberately: `docs/dues/history/SCHEMA-PR-PROPOSAL.md` §4.6), so a consumed month can never become billable again through any currently-approved path. **No overlap is therefore a database guarantee. "No unpaid package" is not** — nothing in the schema prevents a `PACKAGE` row from existing without a settlement; that guarantee is entirely `purchasePackage`'s own transactional design (its atomic obligation-plus-coverage creation, its explicit post-`settleReceipt` check that every required id — including the package's own — actually appears in `settledIds`, and its rollback of everything, including provisional coverage rows, if that check fails). If `purchasePackage` itself had a bug, the database alone would not catch an unpaid package the way it would catch an overlapping one.
- **"At most one payment per receipt" backstop, where a pending-receipt concept exists.** The currency-conversion brief's design for a future `AwaitingRateReceipt` (approved policy, not yet built — §5.3) calls for a DB-level `DuesPayment.resolvedFromReceiptId String? @unique` as the backstop for "at most one resolution per receipt," matching this same pattern; it does not exist yet because the table it would reference does not exist yet.

## 3. Currency conversion (PRs #78–79)

**Design, as it stands today** (`src/lib/dues/ledger/exchange-rate.ts`, `cross-currency-settlement.ts`, `exchange-rate-arithmetic.ts`):

- **Shared/exclusive advisory-lock split, not a single always-exclusive lock.** `enterExchangeRateQuote` (a rate's first entry or correction — an occasional, owner-only write) takes `pg_advisory_xact_lock` (**exclusive**) on a reserved two-integer key (`EXCHANGE_RATE_LOCK_NAMESPACE`, `hashtext(organizationId)`). All four settlement writers (`recordDuesPayment`, `correctLateFeeAndSettle`, `prepayMonthlyObligations`, `purchasePackage`) take `pg_advisory_xact_lock_shared` (**shared**) on the identical key, as their own literal first statement, unconditionally, before any row lock. Multiple settlements — same student, different students, same or different currency — hold the shared lock simultaneously with zero contention among themselves; only a concurrent exclusive request (a rate write) genuinely waits for every open shared holder to release, and no new shared holder is granted while an exclusive holder has it. This closes the real race (a settlement using a rate value a correction is simultaneously replacing) without re-serializing ordinary payment traffic — an earlier version of this design used an unconditional exclusive lock for every settlement, discovered during independent review to be a genuine scalability regression (every settlement for an organization serialized against every other one, same-currency payments included), and corrected before merge.
- **The residual trade-off, stated plainly, not minimized**: a rate write can still temporarily block every open settlement for that organization from acquiring the shared lock — including same-currency ones, since the lock is taken unconditionally regardless of whether conversion is ever needed by that particular settlement. This is real and accepted, not hidden: an owner entering or correcting a rate is an occasional administrative action, not a per-payment hot path.
- **Exact BigInt rational arithmetic, never floating point.** `convertUsdToCrcMinor`/`convertCrcToUsdMinor` use `round_half_up(a/b) = (2a+b) div (2b)`. CRC rounds to the nearest whole colón (multiple of 100 minor units); USD rounds to the nearest cent. Halfway rounds up. Zero tolerance.
- **A confirmed, experimentally-verified dependency on READ COMMITTED isolation — scoped to exactly what was tested.** No `$transaction` call anywhere in this codebase sets `isolationLevel`, so Postgres's default (READ COMMITTED) governs every transaction here — and the whole "a settlement that wakes from a blocked shared-lock wait genuinely sees a just-committed correction" guarantee depends on it. **REPEATABLE READ was directly, experimentally forced and observed**: the settlement woke up correctly, but its snapshot was fixed before the wait resolved, so it read the pre-correction revision even though the correction had already committed — real, reproduced staleness. **SERIALIZABLE was never tested** — nothing here claims to know what it would do, only that it is a different isolation level than the one every transaction actually runs under today. Nothing changed as a result of the REPEATABLE READ finding — every transaction already runs READ COMMITTED by omission — but the dependency is documented plainly, in both `resolveEffectiveQuote`'s own doc comment and this section: **if any caller's transaction is ever changed away from READ COMMITTED, this guarantee must be re-verified against a real concurrent correction before shipping, not assumed to still hold.**
- **Observed transaction-timeout behavior, documented, not changed.** Prisma's own defaults (`timeout: 5000ms`, `maxWait: 2000ms`) govern every ledger transaction; nothing overrides them. A transaction blocked on either advisory lock longer than its 5-second budget is **not** proactively cancelled at Postgres's end — the blocked request genuinely sits until the lock is granted, however long that takes, and only once the response arrives does Prisma notice its own deadline already passed and reject with `PrismaClientKnownRequestError` (code `P2028`, "cannot be executed on an expired transaction"). This surfaces as a **rejected promise**, never a typed `{ ok: false }` refusal, from any of the four settlement writers or `enterExchangeRateQuote` — a caller must be ready for that. The blocked request also keeps occupying a database connection for the full duration of the wait, even after Prisma's own deadline has elapsed; sustained lock contention can therefore reduce available connection-pool capacity. No retry logic exists for this anywhere in this ledger, and none was added — documentation only.
- **Rate scoping is genuinely per-organization for the specific fixture keys tested, verified by two-connection concurrency tests, with a real residual risk stated, not eliminated** (`tests/integration/dues-currency-settlement.test.ts`): two different test organizations' settlements never contend on the shared key1 namespace (proven via `pg_locks` rows scoped by `classid`/`objid::int4`/`objsubid`, not fragile query-text matching, and via `pg_blocking_pids()` for the two original wait tests specifically naming which backend blocks which). The test confirms this for its own two fixture organizations specifically by querying `hashtext()` directly and asserting the two values are in fact distinct — it does not, and cannot, prove no two organizations' `hashtext(organizationId)` values could ever coincidentally collide in general. **The brief's own residual-risk statement (§4.1) is real and not eliminated by anything built**: `hashtext` is a 32-bit function, so two distinct organization ids can map to the same value; if that happens, those two organizations' quote operations would serialize against each other unnecessarily for one transaction's duration. This causes no data confusion — every row is still separated by its own real `organizationId` column and the composite tenant foreign keys, and the advisory lock is used purely for ordering, never as a substitute for tenant scoping — but the possibility of an unnecessary, harmless serialization between two unrelated organizations is real and undisguised, not something any test or implementation here rules out. A same-student proof (`purchase-package.test.ts`) separately confirms two settlements for the *same* student still serialize on the pre-existing student row lock, unaffected by the shared/exclusive split.

**What is explicitly not built yet (PR 3/3, not started)**: `AwaitingRateReceipt` (a CRC receipt recorded with no owner-entered rate yet for its date, settling nothing until one is entered — this behavior is an approved, required policy, not an optional enhancement: see §5.3), `resolvedFromReceiptId`, owner-facing exposure of any of this, and the missing-rate handling in PR #79 stays a plain typed refusal (`rateUnavailable`) rather than the real awaiting-rate behavior.

## 5. Current behavior, historical proposals, pending decisions, and known limitations

### 5.1 Current implemented behavior

- All 15 PRs above are merged to `main` and covered by real-database, integration and unit tests, including genuine two-connection concurrency proofs for every documented race.
- Every ledger writer is reachable only from `src/lib/dues/ledger/`, its own tests, and exactly two named, explicitly authorized runners outside it — `src/lib/dues/monthly-generation.ts` and `src/lib/dues/late-fee-assessment.ts` (`AUTHORIZED_CALLERS`, `tests/unit/dues-ledger-not-exposed.test.ts:19`, which fails if any third importer appears). Neither of those two runners is itself registered with any route, server action, or scheduler/cron entry (`vercel.json` has exactly one, unrelated, cron entry — §7) — "no importer outside the ledger" is not the accurate claim; "two permitted runners exist and neither is wired to anything live" is.
- Currency conversion (USD/CRC, BCR sell rate, owner-entered per date) is fully wired into ordinary payments, prepayment, and package purchases, with the shared/exclusive lock design and the documented READ COMMITTED and timeout limitations described in §3.

### 5.2 Historical proposals, superseded or narrowed by a later decision

- `PROPOSAL.md`'s own revision history names five earlier drafts (v1 through v5) that preceded the current, final `PROPOSAL.md` — those drafts are not copied into this repo (`docs/dues/history/README.md` states the folder holds only the 13 *current* briefs); the current `PROPOSAL.md` is what's here, and it records that those earlier drafts included a partial-payment design, later fully replaced by "full settlement only, no partial payments, no credit" (v6/A5 item 5).
- An early currency-conversion design proposed reusing the existing string-prefix advisory-lock namespace convention (`"namespace:orgId"`) and a wall-clock `enteredAt`-based quote-versioning scheme; both were corrected before implementation (§2, §3).
- PR #79's first implementation used a single, always-exclusive advisory lock for every settlement; corrected to the shared/exclusive split in §3 after independent review found it was a genuine scalability regression, not merely a smaller refinement.

**A note on "approved," used carefully in this document.** The brief files in `docs/dues/history/` contain owner-confirmed policy *alongside* recommendations, rejected alternatives, and designs that were themselves later corrected during review — the two are not the same, and a detail should only be called "approved" or "confirmed" here where a specific policy was actually confirmed as such by the owner, not because it appears in an approved brief's surrounding text. §5.3 and §5.4 below name each approved policy individually rather than treating a whole brief as uniformly approved.

### 5.3 Approved policy, not yet implemented — a third category, distinct from both "current behavior" and "pending decisions"

Each of these is a genuinely confirmed owner decision, verified directly against the brief's own text below — but no merged code implements it yet. None of this should be read as either "how the system behaves today" or "still awaiting a decision":

- **Signup timing (PROPOSAL.md A4/B5, confirmed).** Joining **before** the branch's due day creates the one-time signup charge **and** that same month's recurring `MONTHLY` charge; joining **on or after** the due day creates only the signup charge, and the first recurring charge is the *following* month's, created by the monthly job. **Not implemented**: no `SIGNUP` obligation type exists in the schema yet (`SCHEMA-PR-PROPOSAL.md` §4.4: added later "with `ALTER TYPE ... ADD VALUE`... no data is rewritten") — nothing merged so far creates one.
- **Awaiting-rate receipts (CURRENCY-CONVERSION-BRIEF.md policy 3, approved and required, not optional).** A CRC receipt recorded against a USD obligation with no owner-entered rate yet for its received date must be preserved as its own record — settling nothing, never treated as a partial payment or a credit — until an owner enters the rate. Resolution is **owner-only**; cancellation is **owner-only, requires a stated reason, and implies no refund or settlement**. **Not implemented**: PR #79 (merged) refuses this case with a plain typed refusal (`rateUnavailable`) and creates no record of any kind — none of the capture, resolution, or cancellation behavior exists yet. Scoped as currency-conversion PR 3/3 (§3, §7).
- **A quote correction must warn the owner how many completed payments used the value being replaced (CURRENCY-CONVERSION-BRIEF.md policy 4, approved; those payments are never altered — informational only).** **Not implemented**: `enterExchangeRateQuote` (`exchange-rate.ts`, read in full) performs no such count and issues no such warning anywhere in its current code — this is approved policy PR #78 did not build, not a gap in what's documented here.
- **The resume-charge rule (`ELIGIBILITY-PREREQUISITES-BRIEF.md` §3.4, resolved/confirmed).** Resuming a paused student charges the calendar month **containing the resume date**, in full, with no proration; `dueOn := max(that month's normal configured due date, the resume date)`; `graceDeadline` stays that month's normal configured grace day, unchanged, never recomputed as a duration. **Not implemented**: `resumeStudent` (merged) writes only the status change, its `StudentStatusChange` row, and its audit entry — it calls no obligation-creating function at all. The brief is explicit that this rule is "a specification for the later payment-write integration PR," not something this phase builds; nothing built since has changed that.

### 5.4 Pending, unresolved decisions (no default assumed for any of these — see each brief's own decision register for full context)

- **D1**: CRC-rounding-and-tolerance policy is otherwise resolved (halfway rounds up, zero tolerance, nearest-earlier-quote fallback, §3) — the remaining open item is whatever correction procedure exists beyond the required payment-count warning (§5.3, approved but unbuilt).
- **D9/D13/D14**: the paused/left-to-`INACTIVE`/`ARCHIVED` status mapping and whether a late fee still applies to debt of someone who left; which date counts as "joined" (the form date, or the day staff approve and take payment); and whether the signup price always equals tuition or can be its own setting — all still genuinely open. (Signup *timing itself* — which month gets the first recurring charge — is confirmed policy, not open; see §5.3. D3, "when an unpaid signup charge counts as late," also remains open and belongs with this group.)
- **D4**: refund policy (amount, affected months, coverage release) — explicitly not designed; "waiving an already-paid fee" (§4, PR #75) and "a payment that created prepaid/package obligations cannot be reversed" (§4, PRs #76/#77) are both temporary, conservative refusals pending this decision, not implementations of it.
- **D5**: who besides owners may perform an action that has no owner-only check today. **`recordDuesPayment` specifically has none** (§2) — this is the live, open case D5 governs, not a hypothetical. Every *other* money-affecting writer built so far (`correctLateFeeAndSettle`, `reversePayment`, `waiveLateFee`, `prepayMonthlyObligations`, `purchasePackage`, `enterExchangeRateQuote`) already checks owner-only by its own explicit, confirmed design and is not reopened by this item.
- **D7/D15**: opening-balance handling and switch-over sequencing for existing organizations at activation time — not built; no `OPENING` obligation type exists yet.
- **D8**: individual price exceptions (scholarships, sibling discounts) — deferred, not built.
- **D16**: the "students needing follow-up" dashboard/analytics section's exact thresholds and contact channels — read-only, independent of the ledger, can ship separately; not part of any PR above.
- **Currency-conversion PR 3/3** (§3, §5.3): `AwaitingRateReceipt`, `resolvedFromReceiptId`, and the owner-facing resolution/cancellation UI for a missing-rate receipt — not started, though the policy itself (§5.3) is already approved.
- **Contact-email uniqueness policy** (unrelated to the ledger itself, but a standing open item from the registration-fixes work, PR #61): deliberately left undecided; not resolved by anything in this document.

### 5.5 Known limitations

- **The READ COMMITTED dependency** (§3): every settlement transaction depends on Postgres's default isolation level; REPEATABLE READ was directly tested and confirmed to reintroduce a stale-rate read; SERIALIZABLE was never tested.
- **The transaction-timeout/connection-pool observation** (§3): a lock wait beyond Prisma's 5-second default surfaces as a rejected promise, not a typed refusal, and keeps a database connection occupied for its full duration even past that deadline.
- **A possible, harmless cross-organization advisory-lock collision** (§3): `hashtext(organizationId)` is a 32-bit function; two organizations' ids coincidentally colliding would serialize their quote operations against each other unnecessarily for one transaction's duration, without confusing or exposing either organization's data (tenant scoping is enforced entirely by real `organizationId` columns and composite foreign keys, never by the advisory lock). Not eliminated by anything built; not observed to have happened.
- **`assignment.plan's branch !== academyId`'s unreachable defensive check** (`eligibility.ts`, `docs/dues/history/ELIGIBILITY-PREREQUISITES-BRIEF.md` §5.4): correct today only because no branch-transfer feature exists anywhere in this codebase; explicitly flagged as needing its own history table and its own eligibility-function change the day one is built.

## 6. Inactive billing gates

Every ledger writer is gated by `LedgerActivation` (`src/lib/dues/ledger/activation.ts`): an injected interface whose only production implementation, `inactiveLedgerActivation`, returns `false` for every organization. This is explicitly **not authorization** — it is a test seam and a closed default, stated in the module's own doc comment: *"Before ANY caller is exposed... activation must come from TRUSTED ORGANIZATION STATE read by the server... never from request data and never from a boolean a caller supplies."* No activation table, setting, or flag exists yet; none is invented by anything built so far.

A separate structural test (`tests/unit/dues-ledger-not-exposed.test.ts`) fails if any importer outside `src/lib/dues/ledger/`, its own tests, and the two named `AUTHORIZED_CALLERS` (`monthly-generation.ts`, `late-fee-assessment.ts`) imports a writer — a third file starting to import from the ledger still fails it. A sibling test (`tests/unit/dues-eligibility-not-exposed.test.ts`) does the equivalent for the pure eligibility function, which has no authorized external caller at all. Every writer, and both authorized runners, is additionally registered in `scripts/pending-callers.ts`, the repository's own "built ahead of its caller" tracking list, so CI surfaces every one of these as a deliberate, named, not-yet-exposed piece of work rather than silently forgotten code.

**Flipping this gate is out of scope for everything built in PRs #65–#79.** Nothing in this document proposes or schedules when that happens.

## 7. Remaining rollout prerequisites

Before any organization's real billing could switch to this ledger, all of the following would need to happen — none of it has started:

1. **Payment-write integration**: the legacy payments page, student profile, and record/mark-paid actions would need to read and write the ledger for an activated organization, with the old actions refusing server-side once activated (`PROPOSAL.md` §B10).
2. **Consumer integration**: the portal, roster, payments page, dashboard panel, contact list, weekly digest, and analytics would all need to read the ledger instead of the legacy overdue rule for an activated organization.
3. **Scheduler wiring**: neither the monthly-generation job (PR #71) nor the late-fee assessment runner (PR #72) is registered anywhere — `vercel.json`'s `crons` array has exactly one entry (`/api/cron/weekly-digest`), unrelated to dues. Both are plain, callable functions with no route, action, or cron entry, by deliberate design (§6).
4. **Activation infrastructure itself**: the `LedgerActivation` interface exists; nothing implements it as anything other than "always inactive" yet. Building a real implementation, the readiness checklist it would gate on (policy approved, prices and assignments reviewed, opening balances confirmed, every consumer integrated), and the actual activation control are all future work.
5. **Currency-conversion PR 3/3** (§3, §5.3): `AwaitingRateReceipt` and its resolution/cancellation behavior — this is already **approved, required policy** (policy 3), not something contingent on the owner wanting more than the current plain refusal; it simply has not been built yet.
6. **Enrollment-charge and resume-charge integration**: both rules are confirmed policy (§5.3) but neither is wired to any obligation-creating call. Signup timing (before the due day: signup plus that month's recurring charge; on/after: signup only, next recurring charge the following month) needs the `SIGNUP` obligation type built first. The resume-charge rule (charge the calendar month containing the resume date, in full, no proration, `dueOn := max(that month's normal due date, the resume date)`, `graceDeadline` unchanged) needs `resumeStudent` (or a caller composed with it) to actually call an obligation-creating function in the same transaction — explicitly left to "the later payment-write integration PR" by the brief that resolved the rule, and still true today.
7. **Dev database migration status**: at various points during this feature's construction, the local development database lagged behind main's migrations (documented per-PR in the individual briefs in `docs/dues/history/`); before any real use, confirm the dev database (and any staging/production database) is fully migrated and drift-clean (`pnpm db:check-drift`).
8. **Opening balances and signup/back-billing policy** (D3, D7, D9, D13–D15 above): none of this is built; an organization with existing unpaid periods under the legacy model has no path into this ledger yet. **This is a separate concern from §8's fictional-students statement below** — it is about a *future* real activation with genuinely existing paying students, not about anything required for the current, fictional-data rollout.
9. **UI**: no owner- or staff-facing screen exists for any of `correctLateFeeAndSettle`, `reversePayment`, `waiveLateFee`, `prepayMonthlyObligations`, `purchasePackage`, or `enterExchangeRateQuote` — every one of these is a library function only, exercised so far exclusively by its own tests.

## 8. Fictional students — no real-balance migration required for this rollout

**Every student currently in every environment (development, test, and any organization that has registered so far) is fictional seed or test data.** This was an explicit clarification made during this feature's construction, carried forward here so it is never lost: because no real student's real historical balance exists anywhere yet, **this rollout requires no historical balance import, no back-billing reconciliation, and no data migration to reconcile legacy `PaymentPeriod` rows against invented opening balances.** Every baseline, assignment, and readiness check listed elsewhere in this document (§7) is still required exactly as stated — this statement narrows *what data* those checks would need to process for the current rollout, it does not remove any of the checks themselves.

**This is a statement about the current, fictional-data rollout specifically — not a claim that real-balance import will never be needed.** The day Alliance's own branches (or any future customer) activate this ledger with genuinely existing paying students and real unpaid periods, the "opening balance" mechanism described in `PROPOSAL.md` §B10 (an owner-identified, manually-entered `OPENING` obligation for each existing unpaid period, D7) is the documented design for that — and nothing about it is built yet (§7). These are two different facts: *nothing needs importing for this rollout* (true, confirmed, stated above) and *real-balance import support will be needed for a future real activation* (also true, unaddressed by anything built, tracked as an open rollout prerequisite in §7) — this document does not conflate the two, and a reader should not either.
