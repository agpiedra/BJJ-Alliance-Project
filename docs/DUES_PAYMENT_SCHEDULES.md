## 1. Overview

The dues ledger tracks what a student owes an academy (branch) for tuition, on a monthly or multi-month basis, and how that debt is settled — replacing the legacy `PaymentPeriod` model's single `status` column (`PAID`/`PENDING`/`PROMO`/`EXEMPT`, no due date, no grace, no fee, no partial payment, no exchange rate) with an append-only ledger of obligations, fees, payments and settlements. The legacy model and every legacy payment record are completely untouched — nothing in this feature reads or writes `PaymentPeriod` (`PROPOSAL.md` §B1/§B10), and no organization's real billing behavior has changed as a result of any of it (§7, "Inactive billing gates").

**Core entities** (`prisma/schema.prisma`):

- **`DuesPolicyVersion`** — a branch's due day, grace day, late-fee amount/currency and prepayment-months limit, versioned by effective month. One row per branch per effective month.
- **`PaymentPlanTerms`** — a plan's price, currency and months-covered, versioned by effective month. `monthsCovered = 1` is an ordinary monthly plan; `>= 1` more is a multi-month package.
- **`StudentPlanAssignment`** — which plan a student is on, effective from a given month. `planId: null` is a first-class "explicitly unassigned" value, distinct from "no row yet" (undecided).
- **`StudentStatusChange`** — an append-only history of a student's status (`ACTIVE`/`INACTIVE`/`PENDING`/`ARCHIVED`), the fact the eligibility function reads instead of trusting `Student.status`'s current value for a past month.
- **`DuesObligation`** — one row of debt: `MONTHLY` (recurring tuition for one coverage month), or `PACKAGE` (one multi-month offer, its own price, never late, never partial). Whole-row immutable, including its dates (`prisma/migrations/20260927153000_dues_ledger_schema`'s trigger).
- **`DuesCoverage`** — one row per calendar month an obligation reserves; unconditionally unique per student per month across every obligation type, so a `MONTHLY`, a `PACKAGE`, and any future overlap are all prevented by the same constraint.
- **`DuesLateFee`** — a marker (not a separate amount; the fee is the obligation's own snapshotted `lateFeeAmount`) that a `MONTHLY` obligation is overdue, unique per obligation, with a generic removal marker (`WAIVED` or `VOIDED`) that is complete-or-null and one-time at the database level.
- **`DuesPayment`** / **`DuesSettlement`** — an immutable payment record and the append-only link from a payment to the obligation(s) it settles, one settlement per obligation, at most one *active* (unreversed) settlement per obligation.
- **`ExchangeRateQuote`** — an owner-entered BCR USD sell rate for a specific date, append-only, corrected only by a new, explicitly-numbered `revision` (never an edit), added in the currency-conversion work (§3).

**The "narrow transaction-aware extraction" pattern**, used repeatedly across this feature rather than duplicated or reinvented each time a new writer needs an existing writer's core logic: a public function (e.g. `createMonthlyObligation`, `recordDuesPayment`) opens its own transaction and does its own pre-transaction checks, then delegates to an exported `*InTx` sibling (e.g. `createMonthlyObligationInTx`, `recordDuesPaymentInTx`) that takes an already-open `tx` and does the real work, trusting nothing from its caller — re-checking scope, activation and role itself rather than assuming a caller already did. This is what let `prepayMonthlyObligations` and `purchasePackage` reuse `recordDuesPaymentInTx`'s settlement core, and `correctLateFeeAndSettle` compose the fee-void and the settlement in one transaction, without ever nesting a `prisma.$transaction` inside another (the exact mistake identified and reverted once, in the eligibility-prerequisites work — see `docs/dues/history/ELIGIBILITY-PREREQUISITES-BRIEF.md` §3.4).

**Lock order**, fixed and shared by every writer that touches more than one row: branch (`FOR SHARE` for a ledger writer, `FOR UPDATE` for a configuration correction) → student (`FOR UPDATE`) → terms/policy/assignment (`FOR SHARE` for a ledger writer, `FOR UPDATE` for a correction). Every writer added after the first (`create-monthly-obligation.ts`) took this exact order, verified deadlock-free because every writer's own lock set is a prefix or a strict subset of the same fixed sequence, never a different order (`docs/dues/history/LEDGER-WRITERS-BRIEF.md` §3.1; extended for `assignPlan` in `docs/dues/history/MONTHLY-GENERATION-BRIEF.md` §5; extended again for `lockAssignmentShared` in `docs/dues/history/MONTHLY-PREPAYMENT-BRIEF.md` §5).

## 2. Ledger invariants

- **Money facts are append-only.** No writer updates or deletes a `DuesObligation`, `DuesPayment`, `DuesSettlement` row's substantive fields; a mistake is corrected by a new, explicit row (a reversal marker, a void marker, a new `ExchangeRateQuote` revision), never an edit in place.
- **Whole-row immutability where it matters.** `DuesObligation`'s entire row, including its due/grace dates, is immutable at the database level (`DuesObligation`'s trigger, `20260927153000_dues_ledger_schema`) — rescheduling has no approved policy, so the database gives it no exception.
- **One-time removal/reversal markers, complete or null, enforced by Postgres, not application discipline.** `DuesLateFee`'s `removedAt`/`removalKind`/`removedById`/`removalReason` and `DuesPayment`/`DuesSettlement`'s `reversedAt`/`reversedById`/`reversalReason` are each guarded by a `..._marker_complete` CHECK constraint (all four fields null, or all four set with a non-blank reason) and a `dues_set_once_marker` trigger that rejects any further change once set — a second void, waiver, or reversal attempt is refused by the database itself, independent of whether application code happens to check first.
- **`MAX(x)+1`-under-lock, never a wall-clock timestamp, for anything that needs same-instant ordering.** `StudentStatusChange.sequence` (assigned as `MAX(sequence)+1` under `lockStudent`, `docs/dues/history/ELIGIBILITY-PREREQUISITES-BRIEF.md` §3.2) and `ExchangeRateQuote.revision` (assigned as `MAX(revision)+1` under the exchange-rate advisory lock, §3 below) both exist because a transaction-start timestamp (`createdAt`) cannot reliably reflect true commit order under lock contention — a transaction that began later but queued less can commit first, with an earlier `createdAt` than a transaction that began first but waited longer. This was corrected once during design (the eligibility-prerequisites brief's own revision history) and the lesson was reused deliberately for `ExchangeRateQuote.revision` rather than repeated.
- **DB-level CHECK constraints encode type-specific shape, not just application validation.** `DuesObligation_shape_by_type` requires a `MONTHLY` row to have `monthsCovered = 1` plus `dueOn`/`graceDeadline`/`lateFeeAmount`/`policyVersionId` all set, and a `PACKAGE` row to have `monthsCovered >= 2` with all four of those fields NULL — making "a package is never late" a structural fact, not a convention an application writer could forget.
- **Composite tenant FKs everywhere.** Every dues table carries `organizationId`, with `(organizationId, id)` composite foreign keys throughout, registered in both `tenant-guard.ts`'s and `scoped-client.ts`'s `TENANT_SCOPED_MODELS` (kept in sync by a test) — including `ExchangeRateQuote`, which was briefly missing from both until caught during PR #78's own review and fixed before merge.
- **Unconditional coverage uniqueness is what makes "no unpaid package, no overlap" a structural guarantee rather than a policy.** `DuesCoverage`'s `(studentId, year, month)` uniqueness is unconditional — not scoped by obligation type — so a package's N coverage rows collide with the exact same constraint an ordinary monthly obligation's single row would, and a reversal never releases coverage (deliberately: `docs/dues/history/SCHEMA-PR-PROPOSAL.md` §4.6), so a consumed month can never become billable again through any currently-approved path.
- **"At most one payment per receipt" backstop, where a pending-receipt concept exists.** The currency-conversion brief's design for a future `AwaitingRateReceipt` (§4, PR 3/3, not yet built — see "Pending, unresolved decisions" below) calls for a DB-level `DuesPayment.resolvedFromReceiptId String? @unique` as the backstop for "at most one resolution per receipt," matching this same pattern; it does not exist yet because the table it would reference does not exist yet.

## 3. Currency conversion (PRs #78–79)

**Design, as it stands today** (`src/lib/dues/ledger/exchange-rate.ts`, `cross-currency-settlement.ts`, `exchange-rate-arithmetic.ts`):

- **Shared/exclusive advisory-lock split, not a single always-exclusive lock.** `enterExchangeRateQuote` (a rate's first entry or correction — an occasional, owner-only write) takes `pg_advisory_xact_lock` (**exclusive**) on a reserved two-integer key (`EXCHANGE_RATE_LOCK_NAMESPACE`, `hashtext(organizationId)`). All four settlement writers (`recordDuesPayment`, `correctLateFeeAndSettle`, `prepayMonthlyObligations`, `purchasePackage`) take `pg_advisory_xact_lock_shared` (**shared**) on the identical key, as their own literal first statement, unconditionally, before any row lock. Multiple settlements — same student, different students, same or different currency — hold the shared lock simultaneously with zero contention among themselves; only a concurrent exclusive request (a rate write) genuinely waits for every open shared holder to release, and no new shared holder is granted while an exclusive holder has it. This closes the real race (a settlement using a rate value a correction is simultaneously replacing) without re-serializing ordinary payment traffic — an earlier version of this design used an unconditional exclusive lock for every settlement, discovered during independent review to be a genuine scalability regression (every settlement for an organization serialized against every other one, same-currency payments included), and corrected before merge.
- **The residual trade-off, stated plainly, not minimized**: a rate write can still temporarily block every open settlement for that organization from acquiring the shared lock — including same-currency ones, since the lock is taken unconditionally regardless of whether conversion is ever needed by that particular settlement. This is real and accepted, not hidden: an owner entering or correcting a rate is an occasional administrative action, not a per-payment hot path.
- **Exact BigInt rational arithmetic, never floating point.** `convertUsdToCrcMinor`/`convertCrcToUsdMinor` use `round_half_up(a/b) = (2a+b) div (2b)`. CRC rounds to the nearest whole colón (multiple of 100 minor units); USD rounds to the nearest cent. Halfway rounds up. Zero tolerance.
- **A confirmed, experimentally-verified dependency on READ COMMITTED isolation.** No `$transaction` call anywhere in this codebase sets `isolationLevel`, so Postgres's default (READ COMMITTED) governs every transaction here — and the whole "a settlement that wakes from a blocked shared-lock wait genuinely sees a just-committed correction" guarantee depends on it. Forcing a settlement's transaction to REPEATABLE READ, as a direct experiment, reproduced real staleness: the settlement woke up correctly, but its snapshot was fixed before the wait resolved, so it read the pre-correction revision even though the correction had already committed. Nothing changed as a result of this finding — every transaction already runs READ COMMITTED by omission — but the dependency is now documented plainly, in both `resolveEffectiveQuote`'s own doc comment and this section: **if any caller's transaction is ever changed to REPEATABLE READ or SERIALIZABLE, this guarantee breaks silently and must be re-verified against a real concurrent correction first.**
- **Observed transaction-timeout behavior, documented, not changed.** Prisma's own defaults (`timeout: 5000ms`, `maxWait: 2000ms`) govern every ledger transaction; nothing overrides them. A transaction blocked on either advisory lock longer than its 5-second budget is **not** proactively cancelled at Postgres's end — the blocked request genuinely sits until the lock is granted, however long that takes, and only once the response arrives does Prisma notice its own deadline already passed and reject with `PrismaClientKnownRequestError` (code `P2028`, "cannot be executed on an expired transaction"). This surfaces as a **rejected promise**, never a typed `{ ok: false }` refusal, from any of the four settlement writers or `enterExchangeRateQuote` — a caller must be ready for that. The blocked request also keeps occupying a database connection for the full duration of the wait, even after Prisma's own deadline has elapsed; sustained lock contention can therefore reduce available connection-pool capacity. No retry logic exists for this anywhere in this ledger, and none was added — documentation only.
- **Rate scoping is genuinely per-organization, verified by two-connection concurrency tests** (`tests/integration/dues-currency-settlement.test.ts`): two different organizations' settlements never contend on the shared key1 namespace (proven via `pg_locks` rows scoped by `classid`/`objid::int4`/`objsubid`, not fragile query-text matching, and via `pg_blocking_pids()` for the two original wait tests specifically naming which backend blocks which). A same-student proof (`purchase-package.test.ts`) separately confirms two settlements for the *same* student still serialize on the pre-existing student row lock, unaffected by the shared/exclusive split.

**What is explicitly not built yet (PR 3/3, not started)**: `AwaitingRateReceipt` (a CRC receipt recorded with no owner-entered rate yet for its date, settling nothing until one is entered), `resolvedFromReceiptId`, owner-facing exposure of any of this, and the missing-rate handling in PR #79 stays a plain typed refusal (`rateUnavailable`) rather than the real awaiting-rate behavior. See "Pending, unresolved decisions" below.

## 5. Current behavior, historical proposals, pending decisions, and known limitations

### 5.1 Current implemented behavior

- All 15 PRs above are merged to `main` and covered by real-database, integration and unit tests, including genuine two-connection concurrency proofs for every documented race.
- Every writer is reachable only from `src/lib/dues/ledger/` and its own tests (`tests/unit/dues-ledger-not-exposed.test.ts`, `tests/unit/dues-eligibility-not-exposed.test.ts`) — no route, server action, or scheduler entry calls any of it (§6).
- Currency conversion (USD/CRC, BCR sell rate, owner-entered per date) is fully wired into ordinary payments, prepayment, and package purchases, with the shared/exclusive lock design and the documented READ COMMITTED and timeout limitations described in §3.

### 5.2 Historical proposals, superseded or narrowed by a later decision

- `PROPOSAL.md`'s early drafts (v1–v5, kept as `PROPOSAL-v1-superseded.md` through `-v5-superseded.md` in `docs/dues/history/`, not copied into this repo — only the final `PROPOSAL.md` was) included a partial-payment design, later fully replaced by "full settlement only, no partial payments, no credit" (v6/A5 item 5).
- An early currency-conversion design proposed reusing the existing string-prefix advisory-lock namespace convention (`"namespace:orgId"`) and a wall-clock `enteredAt`-based quote-versioning scheme; both were corrected before implementation (§2, §3).
- PR #79's first implementation used a single, always-exclusive advisory lock for every settlement; corrected to the shared/exclusive split in §3 after independent review found it was a genuine scalability regression, not merely a smaller refinement.

### 5.3 Pending, unresolved decisions (no default assumed for any of these — see each brief's own decision register for full context)

- **D1**: CRC-rounding-and-tolerance policy for cases beyond what §3 already implements is otherwise resolved (halfway rounds up, zero tolerance, nearest-earlier-quote fallback) — the remaining open item is how a *mistyped* quote's correction should notify or affect completed payments beyond the warning already built (§3, PR #78's revision-history mechanism).
- **D3/D9/D13/D14**: signup-charge timing, late-fee applicability to an unpaid signup charge, the "joined" date definition, and whether the signup price always follows tuition — all still open; no `SIGNUP` obligation type exists yet.
- **D4**: refund policy (amount, affected months, coverage release) — explicitly not designed; "waiving an already-paid fee" (§4, PR #75) and "a payment that created prepaid/package obligations cannot be reversed" (§4, PRs #76/#77) are both temporary, conservative refusals pending this decision, not implementations of it.
- **D5**: who besides owners may record ordinary payments, assign students, or perform other non-owner-restricted actions — every money-affecting writer built so far is owner-only by explicit, verified design choice, but this question for the *general* case (e.g. a Director recording an ordinary on-time payment) remains open.
- **D7/D15**: opening-balance handling and switch-over sequencing for existing organizations at activation time — not built; no `OPENING` obligation type exists yet.
- **D8**: individual price exceptions (scholarships, sibling discounts) — deferred, not built.
- **D16**: the "students needing follow-up" dashboard/analytics section's exact thresholds and contact channels — read-only, independent of the ledger, can ship separately; not part of any PR above.
- **Currency-conversion PR 3/3** (§3): `AwaitingRateReceipt`, `resolvedFromReceiptId`, and any owner-facing exposure of a missing-rate receipt — not started.
- **Contact-email uniqueness policy** (unrelated to the ledger itself, but a standing open item from the registration-fixes work, PR #61): deliberately left undecided; not resolved by anything in this document.

### 5.4 Known limitations

- **The READ COMMITTED dependency** (§3): every settlement transaction depends on Postgres's default isolation level; changing any caller to REPEATABLE READ or SERIALIZABLE would silently reintroduce a stale-rate read.
- **The transaction-timeout/connection-pool observation** (§3): a lock wait beyond Prisma's 5-second default surfaces as a rejected promise, not a typed refusal, and keeps a database connection occupied for its full duration even past that deadline.
- **`assignment.plan's branch !== academyId`'s unreachable defensive check** (`eligibility.ts`, `docs/dues/history/ELIGIBILITY-PREREQUISITES-BRIEF.md` §5.4): correct today only because no branch-transfer feature exists anywhere in this codebase; explicitly flagged as needing its own history table and its own eligibility-function change the day one is built.
- **`feeAlreadyAssessed` becomes live and reachable** (§4, PR #72) with no resolution path for staff until a waiver/void writer exists — resolved in PRs #73/#75, but recorded here as the reason those two PRs were sequenced immediately after assessment rather than deferred.

## 6. Inactive billing gates

Every ledger writer is gated by `LedgerActivation` (`src/lib/dues/ledger/activation.ts`): an injected interface whose only production implementation, `inactiveLedgerActivation`, returns `false` for every organization. This is explicitly **not authorization** — it is a test seam and a closed default, stated in the module's own doc comment: *"Before ANY caller is exposed... activation must come from TRUSTED ORGANIZATION STATE read by the server... never from request data and never from a boolean a caller supplies."* No activation table, setting, or flag exists yet; none is invented by anything built so far.

A separate structural test (`tests/unit/dues-ledger-not-exposed.test.ts`) fails if anything outside `src/lib/dues/ledger/` and its own tests imports any writer, and a sibling test (`tests/unit/dues-eligibility-not-exposed.test.ts`) does the same for the pure eligibility function. Every writer is additionally registered in `scripts/pending-callers.ts`, the repository's own "built ahead of its caller" tracking list, so CI surfaces every one of these as a deliberate, named, not-yet-exposed piece of work rather than silently forgotten code.

**Flipping this gate is out of scope for everything built in PRs #65–#79.** Nothing in this document proposes or schedules when that happens.

## 7. Remaining rollout prerequisites

Before any organization's real billing could switch to this ledger, all of the following would need to happen — none of it has started:

1. **Payment-write integration**: the legacy payments page, student profile, and record/mark-paid actions would need to read and write the ledger for an activated organization, with the old actions refusing server-side once activated (`PROPOSAL.md` §B10).
2. **Consumer integration**: the portal, roster, payments page, dashboard panel, contact list, weekly digest, and analytics would all need to read the ledger instead of the legacy overdue rule for an activated organization.
3. **Scheduler wiring**: neither the monthly-generation job (PR #71) nor the late-fee assessment runner (PR #72) is registered anywhere — `vercel.json`'s `crons` array has exactly one entry (`/api/cron/weekly-digest`), unrelated to dues. Both are plain, callable functions with no route, action, or cron entry, by deliberate design (§6).
4. **Activation infrastructure itself**: the `LedgerActivation` interface exists; nothing implements it as anything other than "always inactive" yet. Building a real implementation, the readiness checklist it would gate on (policy approved, prices and assignments reviewed, opening balances confirmed, every consumer integrated), and the actual activation control are all future work.
5. **Currency-conversion PR 3/3** (§3, §5.3): `AwaitingRateReceipt` and its resolution/cancellation UI, if the owner wants the awaiting-rate case to be more than a plain refusal.
6. **Dev database migration status**: at various points during this feature's construction, the local development database lagged behind main's migrations (documented per-PR in the individual briefs in `docs/dues/history/`); before any real use, confirm the dev database (and any staging/production database) is fully migrated and drift-clean (`pnpm db:check-drift`).
7. **Opening balances and signup/back-billing policy** (D3, D7, D9, D13–D15 above): none of this is built; an organization with existing unpaid periods under the legacy model has no path into this ledger yet.
8. **UI**: no owner- or staff-facing screen exists for any of `correctLateFeeAndSettle`, `reversePayment`, `waiveLateFee`, `prepayMonthlyObligations`, `purchasePackage`, or `enterExchangeRateQuote` — every one of these is a library function only, exercised so far exclusively by its own tests.

## 8. Fictional students — no real-balance migration required for this rollout

**Every student currently in every environment (development, test, and any organization that has registered so far) is fictional seed or test data.** This was an explicit clarification made during this feature's construction, carried forward here so it is never lost: because no real student's real historical balance exists anywhere yet, **this rollout requires no historical balance import, no back-billing reconciliation, and no data migration to reconcile legacy `PaymentPeriod` rows against invented opening balances.** The "opening balance" mechanism described in `PROPOSAL.md` §B10 (an owner-identified, manually-entered `OPENING` obligation for each existing unpaid period) remains the documented design for a future real-world activation with genuinely existing paying students — but nothing about *this* rollout's current state depends on it existing yet, and nothing here should be read as implying real students' balances need to be imported before this ledger can eventually be turned on for Alliance's own two existing branches.
