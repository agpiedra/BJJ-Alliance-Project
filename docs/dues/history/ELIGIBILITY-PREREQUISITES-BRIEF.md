## 1. Why this phase, and what it unblocks

PR 4a's writers (`createMonthlyObligation`, `recordDuesPayment`) exist but have no caller. The **monthly job** — the thing that will actually call `createMonthlyObligation` every month for every eligible student — needs two facts per student per month that nothing today records: **was this student eligible on that month's generation date**, and **which plan were they on**. Verified against merged main:

- **No status history exists.** No `StudentStatusChange` table, no code that reads or writes one.
- **No code path ever sets `INACTIVE`** ("paused" has no writer today). The five status writers are: `createStudent` (`create-student-action.ts:142`, sets `ACTIVE` directly — a staff-entered student, no approval step), `signup` (`o/[orgSlug]/signup/actions.ts:165`, sets `PENDING` — the public self-signup path), `approveStudent` (`students/[id]/actions.ts:437-439`, `PENDING` to `ACTIVE`), `archiveStudent` (`:257`, `ARCHIVED`, keeps `statusBeforeArchive`), `restoreStudent` (`:340-357`, verified: **not** unconditionally `ACTIVE`. Refuses (`notArchived`) unless the student is currently `ARCHIVED`. Restores to the stored `statusBeforeArchive` when one exists and it isn't itself `ARCHIVED`; otherwise (archived before that column existed, or a stored value of `ARCHIVED`) falls back to `PENDING`).
- **No assignment exists.** `StudentPlanAssignment` (id, organizationId, studentId, `planId` nullable, effectiveYear, effectiveMonth, createdById, createdAt; unique per student per month; tenant-registered) is a schema-only table with no writer.

This phase builds exactly those two facts, atomically and honestly, so the monthly job (a later PR) can be a thin, dark, fully-tested piece of code with no judgment calls left in it.

## 3. Status history

### 3.1 The status fact and the billing effect are two different things

This phase writes exactly one kind of fact — **"this student's status became X, effective on calendar date D"** — for every status-changing action. It does **not** decide, anywhere in this section, what that fact means for billing. That question has exactly one owner: the pure read function in **6.2**, which a delayed or on-time monthly job calls identically, for whichever month it is asking about. Keeping these separate is what makes "a delayed job reaches the same result as an on-time job" true by construction rather than by care: the read function is a pure function of the *history*, never of *when it happens to be asked*, so re-running it for October in December after an outage returns the exact same answer it would have returned on October 1st.

### 3.2 `StudentStatusChange`, and same-day ordering (a calendar date alone cannot order two events)

`StudentStatusChange`: `id`, `organizationId`, `studentId`, `status` (`StudentStatus`), `effectiveOn` (`Date`, the branch's calendar date — the business-meaningful fact: "took effect from this day"), `sequence` (`Int`, see below — the ordering fact), `source` (`EVENT` | `BASELINE`), `actorId` (nullable — a real actor for every action below; null is reserved for a future automated writer, none exists yet), `createdAt` (`DateTime`, the real insert instant, kept for audit/display only — **not** used for ordering, see below). Index `(studentId, effectiveOn, sequence)`; `@@unique([studentId, sequence])`. Tenant-registered like every other dues table. **Append-only, no correction path in this PR** (5.1).

**A calendar date cannot tell you whether a pause on the 1st happened before or after that same day's monthly-job generation instant, or whether an archive and a restore submitted seconds apart on the same day landed in the order staff intended — and `createdAt` cannot safely settle it either.** Postgres's `now()` (what `createdAt`'s default resolves to) is fixed at the *start* of a transaction, not at the moment a row is actually inserted. Two transactions queued behind the same student-row lock can commit in the opposite order from the one their `createdAt` values suggest — a transaction that began later but waited less can acquire the lock and insert first, with a `createdAt` earlier than a transaction that began first but queued longer behind something unrelated. A tie-breaker built on `createdAt` would then occasionally disagree with the actual serialized order the lock enforced — silently, since both rows still look plausible. Two things fix this together, not one alone:

1. **A deterministic per-student sequence, assigned inside the lock, not a timestamp.** Every status-changing action locks the student row (`FOR UPDATE`) inside its transaction — reusing `lockStudent` from `src/lib/dues/ledger/common.ts` — **before** reading the current status and **before** computing `sequence := (SELECT COALESCE(MAX(sequence), 0) + 1 FROM "StudentStatusChange" WHERE "studentId" = ...)`. Because the lock forces every concurrent writer for this student to fully serialize, this read-then-insert cannot race: a second transaction's `MAX` query cannot even start until the first transaction's row has committed and the lock has been released, so it always counts the first transaction's row. `sequence` reflects the true commit order by construction, not by hoping a timestamp lines up with it; the `@@unique([studentId, sequence])` constraint turns that into a database-enforced guarantee, not just an application intention. "The student's status as of generation date G" is then: among rows with `effectiveOn < G` (strict — see 3.3), the one with the greatest `(effectiveOn, sequence)` pair. This is the same "latest version on or before the target" shape as PR 1's `priceFor` and this brief's own 6.2, extended with the ordering guarantee same-day events need and versioned tables (PaymentPlanTerms, DuesPolicyVersion) didn't (their `effectiveMonth` already had month granularity with an application-level uniqueness check; a status change has no such uniqueness — two events genuinely can land on the same calendar day).
2. **The one exception: `createStudent` and `signup` need no lock for their first row.** Both insert a brand-new `Student` row (a fresh, randomly generated `id`) and that student's first `StudentStatusChange` row in the same transaction. There is nothing to lock — a row that does not yet exist cannot be locked — and by construction nothing else can reference this student's `id` until this same transaction commits it into existence, so no concurrent writer can ever be racing for "this student's first row." Its `sequence` is hardcoded to `1` (there is nothing yet to take a `MAX` of), and the foreign key from `StudentStatusChange.studentId` to `Student.id` is satisfied because the student row is inserted first, earlier in the same transaction, before the status row. Every other action in the table below already has an existing student row to lock, so it goes through the `MAX`+1 path in point 1.
3. **The lock also keeps concurrent actions from racing each other's preconditions.** Two concurrent `pauseStudent` calls for one student are serialized by the same `lockStudent` call: the second one re-reads status under the lock and finds `INACTIVE` already, so its own precondition check (below) refuses it — there is no window where two `INACTIVE` rows, or an inconsistent status-column-versus-latest-history-row state, can be created. The status column, the history row and its `sequence` are written in the **same transaction**, so an audit row can never exist without its status change nor a status change without its history row (the same discipline `archiveStudent` already uses today).

One row per action, all under the lock described above:

| Action | New `StudentStatusChange` row | Precondition (refuses otherwise) |
|---|---|---|
| `createStudent` | `status: ACTIVE`, `effectiveOn`: today in the branch's timezone | none (a new row) |
| `signup` | `status: PENDING`, `effectiveOn`: today | none (a new row) |
| `approveStudent` | `status: ACTIVE`, `effectiveOn`: today | current status is `PENDING` (already enforced today) |
| `archiveStudent` | `status: ARCHIVED`, `effectiveOn`: today | none (already archives from any status today) |
| `restoreStudent` | `status`: the stored `statusBeforeArchive`, or `PENDING` when there is none (verified against `[id]/actions.ts:340-357`; **not** unconditionally `ACTIVE`) — `effectiveOn`: today | current status is `ARCHIVED` (already enforced today, `notArchived`) |
| `pauseStudent` **(new)** | `status: INACTIVE`, `effectiveOn`: today | **current status is `ACTIVE`** — refuses a `PENDING`, `ARCHIVED` or already-`INACTIVE` student, so pausing can never be used to skip approval or restoration |
| `resumeStudent` **(new)** | `status: ACTIVE`, `effectiveOn`: today | **current status is `INACTIVE`** — symmetric to `restoreStudent`'s `ARCHIVED`-only precondition |

**Existing debt is untouched by any of this, at any status.** Pausing (or archiving) writes nothing to any ledger table; every unpaid `DuesObligation` stays exactly as it is, still payable via PR 4a's `recordDuesPayment` regardless of the student's current status — already confirmed in the merged ledger writer (`recordDuesPayment` does not check student status at all; tested: "an archived student's existing debt stays payable"). **Absence never changes billing (confirmed, unchanged):** neither `pauseStudent` nor `resumeStudent` is triggered by non-attendance; they exist only as explicit staff actions, exactly like `archiveStudent` today. Nothing in this phase reads `AttendanceRecord`.

### 3.3 The billing rule, worked through

**Corrected rule (this revision fixes a boundary bug in the previous draft):** a month M's obligation is created only if the student's status, evaluated **strictly before M begins** — the latest `StudentStatusChange` row with `effectiveOn < G(M)` (the 1st of M), ordered by `(effectiveOn, sequence)` from 3.2 — was `ACTIVE`. The comparison is **strict `<`, not `<=`**. Any status change effective **on or after** the 1st of M affects M+1 onward; it can never affect M itself. The previous draft used `<=` and additionally, in one place, compared against "the job's own read instant" — both wrong: `<=` would make a pause dated the 1st of M wrongly cancel M's own obligation, and comparing against a live instant contradicts 3.1's own promise that the function reads only committed history, never "now." Neither survives this revision; there is no `now()` anywhere in 6.2.

**Note this is unrelated to the join-timing rule (A4).** A4 governs when a *new* student's recurring charge starts, relative to the plan's due day, and is unchanged by anything here: joining before the due day bills that month's recurring charge too (plus signup, same month); joining on or after the due day skips straight to next month's recurring charge. That is a due-day-relative rule about a brand-new enrollment's first charge. The eligibility cutoff here is a month-boundary rule about an *existing* student's ongoing status, with no due-day dependency at all. The two are separate mechanisms; neither one is precedent for the other, and this brief changes neither.

**Worked examples, all against the corrected strict-`<` rule:**

1. **Pause on the 1st: that month remains billable.** Ana is `ACTIVE` through August. `pauseStudent` runs with `effectiveOn = Oct 1`. For October's cutoff (`G(October) = Oct 1`), the rule looks for rows with `effectiveOn < Oct 1` — the Oct 1 pause itself does not qualify (Oct 1 is not `< Oct 1`). The latest qualifying row is still August's `ACTIVE` status, so October's obligation **is** created. Only November's cutoff (`Nov 1`) sees the Oct 1 pause (`Oct 1 < Nov 1`) and skips November.
2. **Pause later in the month: same result.** Same student, `pauseStudent` instead runs with `effectiveOn = Oct 25`. October's cutoff is still `Oct 1`, and `Oct 25` is not `< Oct 1` either — same as case 1, October is unaffected regardless of which day inside it the pause lands on. Only November is skipped. This is also what makes the pause on the 1st and the pause on the 25th behave identically for the month they're dated in: a status change can never reach back and cancel the month it happens during, only the one after it.
3. **Pause then resume, same month.** Paused `effectiveOn = Sep 5`, resumed `effectiveOn = Sep 20`. Neither affects September itself (both fail September's `< Sep 1` cutoff). For October's cutoff (`< Oct 1`), both rows qualify; the later one by `(effectiveOn, sequence)` is the Sep 20 resume, so October's status is `ACTIVE` — October is created normally, exactly as if neither action had happened. A same-month pause-and-resume nets to zero effect on any month, ever.
4. **Multiple status changes on the same day.** Staff mis-click resume then correct it with pause, both `effectiveOn = Sep 20`. `sequence` (not `createdAt`, per 3.2) breaks the tie: whichever row's transaction actually committed second under the student lock has the higher `sequence`, and that is the one that determines status as of end-of-September for October's cutoff — here, the pause, since it was the corrective second click. If the clicks had happened in the other order, the result would flip. Either way the answer tracks the true order the actions executed in, which is exactly what `sequence` (unlike a timestamp) is built to guarantee.
5. **Delayed generation matches on-time generation.** The monthly job is due to run Oct 1 but crashes and doesn't recover until Nov 15. When it finally calls `eligibleAndAssigned(..., October)`, it reads the same history rows with the same `Oct 1` cutoff it would have used on Oct 1 itself — nothing about the real date `Nov 15` enters the function. Even if the student was also paused on `Oct 10` in the meantime, that row still has `effectiveOn = Oct 10`, which is not `< Oct 1`, so it still has zero effect on October's already-fixed answer. Asked on Oct 1 or asked on Nov 15, October's answer is identical (3.1).

The eligibility function in 6.2 implements only this rule; it has no branch for "was recently resumed" and needs none — resume's own obligation, when one is created, is written directly by `resumeStudent` (3.4), never by 6.2 or the monthly job.

### 3.4 Resolved: resume charges its own calendar month in full, no proration

**Decided:** on resume, the branch-local calendar month **containing the resume date** — not any earlier month skipped while paused — is charged at the plan's full configured monthly price. No proration. Earlier skipped months are never backfilled; that part of 3.3's mechanical default was already correct and is unchanged.

**Coverage month = the calendar month of the resume date, always — not the last unbilled month.** A student paused since August who resumes October 10 gets **October's** obligation, not a late-arriving September one; September stays permanently unbilled (3.3's ordinary "generation date already passed" outcome, untouched by resume).

**`dueOn` and `graceDeadline`, corrected:**

```
dueOn        := max(that coverage month's normal configured due date, the resume date)
graceDeadline := that coverage month's normal configured grace deadline — a fixed
                 day of the FOLLOWING month, taken unchanged, never recomputed
```

The grace setting is a **configured day-of-month, inclusive, of the month after `dueOn`'s month** — not a duration — and resume must not silently turn it into one by adding a day-count to a shifted `dueOn`. It is read as-is from the coverage month's normal terms, exactly as `createMonthlyObligation` already computes it for a non-resume obligation in that month.

**Worked examples (Alliance: due day 20, grace day 5 of the following month):**

| Resume date | Coverage month | `dueOn` | `graceDeadline` |
|---|---|---|---|
| Sep 12 | September | Sep 20 (normal due date; `12 < 20`) | Oct 5 (September's normal grace, unchanged) |
| Sep 25 | September | Sep 25 (`max(20, 25)`; due day already passed) | Oct 5 (September's normal grace, still unchanged) |
| Oct 10 | October | Oct 20 (`max(20, 10)`) | Nov 5 (October's normal grace, unchanged) |

Because the coverage month is always "today's own month," its due date can already be behind the resume date, but its grace deadline — always early in the *next* month — cannot be: there is no case where a freshly-created resume obligation is born already past its own grace deadline. That is what removes any late fee for paused time, with one rule, no reset mechanism needed.

**Existing obligations and package coverage: never touched, never duplicated.** These are two separate, already-existing guarantees, not one — correcting an imprecise description from earlier discussion:

- The `MONTHLY`-obligation-per-student-per-month unique key (PR 2A/2B) is what prevents a *second* `MONTHLY` row for a month that already has one. `createMonthlyObligation` already handles this by returning the **existing row unmodified** — not an error, not a new row, nothing rescheduled, no fee touched.
- `DuesCoverage`'s unconditional uniqueness is the **separate** guarantee that a month already covered by a package cannot also get a `MONTHLY` obligation. `createMonthlyObligation` already handles this by returning the typed refusal **`coverageTaken`** — an explicit result, not a silent no-op.
- `createMonthlyObligation` does **not** uniformly "do nothing on conflict"; it returns two different, already-defined outcomes for these two different situations, and `resumeStudent` treats both the same way: as a successful resume with **no new obligation needed**, never as a failure to retry or override. Existing debt (any obligation, any status) is never touched by resume, per 3.2's existing invariant.

**Not implemented by this PR — this section is a specification for the later payment-write integration PR.** This PR's `resumeStudent` writes only the status column, its `StudentStatusChange` row (with its `sequence`, 3.2) and its `AuditLog` entry, atomically, exactly like every other status action in this brief. It does **not** call `createMonthlyObligation`, gated or not.

**Why not composed here, corrected from an earlier draft.** That draft proposed calling `createMonthlyObligation` from inside `resumeStudent`'s own transaction, reusing the student lock already held. That does not work as described: `createMonthlyObligation` owns its own transaction and its own lock order — branch `FOR SHARE` **before** student `FOR UPDATE`. Calling it from a transaction that already holds the student lock does not share that transaction, and takes the locks in the reverse of `createMonthlyObligation`'s own order (student before branch), which can block or deadlock against a concurrent call that takes the correct order. This PR does not attempt that composition, and does not refactor the ledger to accommodate it.

**Left for the payment-write integration PR to design, using the rule above as its specification:** one shared transaction spanning both the status change and the obligation write; `createMonthlyObligation`'s existing lock order preserved exactly (branch, then student, then terms/policy — never reversed); and a trustworthy read of `LedgerActivation`'s state inside that same shared transaction, not merely the injected default checked incidentally elsewhere. Whoever builds that PR starts from the coverage-month/`dueOn`/`graceDeadline`/dedup rules above; `resumeStudent` itself never touches the ledger and needs no change when that PR ships.

**Ledger no-caller guard: unchanged, intact, not touched by this PR.** `resumeStudent` is not an importer of anything under `src/lib/dues/ledger/`. `tests/unit/dues-ledger-not-exposed.test.ts` needs no change here.

## 4. Baseline: recording where existing students stand, without inventing the past

**The problem `StudentStatusChange` alone doesn't solve:** the moment this migration ships, every *existing* student (created before this phase) has zero rows in the new table. If the monthly job trusted an empty history as "never eligible," every current student would silently stop being billable forever. If it trusted the student's *current* `status` column as if it had always been that, it would fabricate history for dates before the table existed.

**No organization-level timezone is invented, and no separate "trusted from" setting is added.** A student's baseline date is captured in **their own home branch's local date** (`Academy.timezone` via `student.homeAcademyId` — the same field every other branch-local date in this codebase already uses), never an organization-wide one. And rather than a separate `statusHistoryTrustedFrom` field the eligibility function has to remember to check, "undecidable" is defined directly as **"no `StudentStatusChange` row exists with `effectiveOn` strictly before G(M)"** (the same strict cutoff 3.3/6.2 use for everything else) — once baseline gives every existing student their own row, that is *already* the honest answer for any month before it, with no second field that could ever disagree with the rows themselves. (A separate, later concern — "has baseline actually been run for this whole organization, as a precondition for activation" — belongs to the activation readiness checklist in a much later phase, which already lists "no student without a baseline or event row" as its own check; it is not something the per-student eligibility function needs to re-derive here.)

**The baseline action:**
- One **owner-reviewed, explicit** action, safe to run at any time and as many times as needed.
- For **every student who currently has zero `StudentStatusChange` rows**, in a transaction that **locks that student's row first** (reusing the same `lockStudent` primitive as every other status action in 3.2 — this serializes baseline against a concurrent real event for a student nobody has ever touched before): re-check under the lock that the student still has zero rows, then write **exactly one**: `status` = that student's **current** `Student.status`, `source: BASELINE`, `effectiveOn` = today in **that student's own branch's** timezone.
- **A repeated run moves nothing and backdates nothing.** A student who already has *any* row — a `BASELINE` row from an earlier run, or a real `EVENT` row from an action that happened since — is left alone: the "zero rows" check, re-verified under the lock, is what makes this true, not a separate idempotency flag. A student first discovered on a *later* run gets a `BASELINE` row dated at **that run's** date, never backdated to an earlier run's date — there is no shared "the baseline date" to backdate to, since each student's row is captured independently, at the moment they are actually processed.
- **Never fabricates anything before a student's real first row.** If a student's very first `StudentStatusChange` row turns out to be a real `EVENT` (because some action — say `archiveStudent` — ran for them before baseline was ever run for the organization), baseline correctly never touches that student at all (the zero-rows check excludes them), and nothing before that `EVENT` row is ever asserted, guessed, or backfilled. The earliest row a student has, whatever its `source`, is the earliest known fact about them; anything strictly before it stays undecidable, forever, for that student — never fabricated by a later baseline run trying to fill the gap.
- A student who is `PENDING` at baseline time gets a `BASELINE` row saying `PENDING` (not eligible); if later approved, `approveStudent`'s own `EVENT` row makes them eligible from that point, same as any newly-approved student.

## 5. Unresolved decisions (blocking only where marked; each with an example and a recommendation)

### 5.1 Does a wrong `StudentStatusChange` row need a correction action in this phase?

*Example:* staff mis-click `archiveStudent` for the wrong student, then immediately `restoreStudent` them. Two real events are recorded (archived, then restored) — history is accurate, nothing needs correcting. But if staff instead need to say "that archive event on the 3rd never should have happened, pretend it didn't," there is today no way to edit or annotate a `StudentStatusChange` row.

**Recommendation: no correction path in this phase.** The two real actions above already self-correct through further real actions (archive-then-restore leaves an honest, if slightly noisy, history — exactly like the audit log already does elsewhere in this codebase, per the standing "audit log is never state, but it is also never edited" rule). A dedicated correction/annotation mechanism is a bigger, separate design question (who may do it, does it need a reason, does it retroactively change past obligations) that nothing in this phase or the monthly job actually needs answered — **not blocking**, deferred to whichever later phase first needs it.

### 5.2 Baseline idempotency and timezone — **resolved by the redesign in section 4, not a decision left open**

The earlier version of this brief asked whether a repeated baseline run should be a no-op or a refusal, and whether it needed an invented organization-wide timezone. Both questions are now answered by construction rather than by policy choice: baseline only ever touches students with **zero** existing rows (re-checked under a lock, section 4), so a repeat run is inherently a no-op for anyone already captured; and each student's date is their **own branch's** local date, so there is no organization-wide timezone to define in the first place. Nothing here needs your decision.

### 5.3 Permissions — **approved**

Pause and resume: owners and the student's own-branch Director, the same gate `archiveStudent`/`restoreStudent` already use. Baseline: owners only. Plan assignment and its correction: **owners only** (6.1) — not inferred from the roster-management gate above; assigning a plan is a money-adjacent decision (it determines what a student will be charged), unlike pausing or resuming, which only change whether a student is billed at all, not what.

### 5.4 Branch transfer: corrected, not resolved — there is no transfer flow, anywhere, today

The earlier version of this brief said a student "assigned to Escazú's Monthly plan is later moved to Escalante (`updateStudent`'s existing `homeAcademyId` change...)" — **that was wrong, and it's worth being explicit that it was wrong, not merely imprecise.** Verified directly against `[id]/actions.ts:88-91` and `updateStudentSchema` (lines 24-36): `homeAcademyId` is not in the schema `updateStudent` accepts, is not in the `after` object it writes, and the function's own doc comment says so outright — *"`homeAcademyId` and `status` are deliberately not editable here — academy transfer isn't a feature this task builds."* No other writer touches it either (grepped every `homeAcademyId:` assignment in the codebase: all of them are `where`/`select` clauses reading it, never an update). **There is no branch-transfer feature anywhere in this codebase, not merely one this phase doesn't build.**

That closes the specific example, but the underlying question the user is right to ask still needs an honest answer: **how does the design stay correct if a transfer feature is ever added later, given a schema column that theoretically *could* be updated even though nothing does today?**

- `DuesObligation.academyId` is already snapshotted at creation and immutable (PR 2B's trigger), so **every past obligation is permanently correct regardless of what happens to the student's `homeAcademyId` afterward** — a past month is never re-evaluated using today's branch, because a past month's obligation, once created, is never re-evaluated at all.
- The eligibility function (6.2), when deciding whether to **create** a new obligation for a future or current month, currently reads the student's **current** `homeAcademyId` — which is safe **only because that value has never changed for any student, ever**, a genuine invariant of this codebase today, not a coincidence: it is set once at `createStudent`/`signup` and nothing since has ever written to it.
- **This invariant would break the day a transfer feature is added**, and 6.2 is written with an explicit comment saying so: using "current `homeAcademyId`" to decide a **past** month's eligibility would then silently use *today's* branch instead of the branch the student was actually at when that month's obligation should have been generated. If a transfer feature is ever built, it needs its **own** history table (the same shape as `StudentStatusChange` — an append-only, effective-dated log), and 6.2 would need to read "the branch as of G(M)" from it, exactly the way it already reads status. **Not blocking this phase** — there is no feature and no history to design around yet — but flagged here so the day someone adds `updateStudent`'s missing branch-transfer support, this comment is what tells them to come back here first.

## 6. Assignment writer, and the eligibility-and-assignment read

### 6.1 `StudentPlanAssignment` writer — owners only

`assignPlan(context, studentId, planId | null, effectiveMonth)`, **owners only** (approved: not inferred from the roster-management gate pause/resume/archive use — assigning a plan decides what a student will be charged, a money-adjacent decision, not a roster one).
- Re-reads student, scoped to the organization; branch checked with `isAcademyInTenantScope` (the pattern every writer in this codebase already follows).
- `planId: null` is a first-class value: **"explicitly unassigned from this month"** (already the schema's own comment). Distinguishes "we haven't gotten to this student yet" (no row at all for that month — undecidable, section 6.2) from "this student explicitly has no plan from this month" (a row exists, with `planId = null` — decided, and decidedly nothing).
- When `planId` is not null: the plan must belong to the student's branch (re-read, tenant-scoped), and **must not be a package plan** (reuse `NOT_PACKAGE_PLAN` / `isPackagePlan` from PR 3 — an ordinary effective-month assignment is for the monthly job; packages are bought explicitly, never assigned this way, per the existing package-isolation design).
- Effective month judged in the branch's timezone (`currentMonthIn`, the same helper PR 3 and PR 4a both already use); a month strictly in the past is refused, matching PR 3's convention for configuration versions. A month already assigned is refused with the existing row's month named (append-only, no silent overwrite).
- **Correction: the exact same protections PR 3's configuration corrections already have, for the same reasons.** A strictly-future assignment may be corrected in place: an `expectedRevision` token (the same `versionRevision`-style hash PR 3 uses) must match the row's current values, so a stale edit — two owners editing the same future assignment from the same starting point — is refused, not silently overwritten; the correction and its before/after `AuditLog` row are written atomically; current and past assignments are never editable, full stop.
- **No separate "referenced by an obligation" trigger is needed by today's writers — but this is conditional on those writers, not a permanent guarantee, and it's worth being precise about the difference.** PR 2B protects a *future* `PaymentPlanTerms`/`DuesPolicyVersion` row because a *prepayment* can be created against it **before its month arrives** (D25's whole reason for existing). Nothing that exists today ever creates an obligation from a **future** assignment: `createMonthlyObligation` only runs for the month a job is currently processing, so by the time any obligation could reference month M's assignment, M's assignment has already become "current" under the correction rule's own definition, and current assignments are already immutable. That is true only because of what current writers happen to do, not because of anything structural that would stop a future writer from doing otherwise.
- **The prerequisite this creates for prepayment, stated now so it isn't rediscovered later:** prepayment is an approved future feature (PROPOSAL.md A6/A7) whose entire purpose is to create an obligation for an explicitly future coverage month — which means it *will* need to read a still-future assignment to know which plan to price that month against, the exact scenario this bullet says cannot happen today. Before prepayment's writer ships, one of two things must be true, and both amount to the same real invariant: **a correction must never be able to alter the assignment (or terms) that an already-created financial record was built from.**
  1. Prepayment's writer snapshots the assignment (and terms) it used onto the obligation at creation time, exactly as `DuesObligation` already snapshots amount, currency and due date (PR 2B) — a later correction to the assignment then simply cannot reach an obligation that no longer reads it live; or
  2. `StudentPlanAssignment` gets the same reference-protecting trigger pattern PR 2B already built for `PaymentPlanTerms`/`DuesPolicyVersion` (`dues_terms_referenced_guard` / `dues_policy_referenced_guard`) — locking a referenced future assignment against correction the same way a referenced future terms/policy version already is.

  This phase's `assignPlan` correction path needs neither mechanism yet, because no writer that exists today can reference a future assignment. That is a statement about the current writers, not a proof about the design — whoever builds prepayment's writer must re-verify this section first, not carry forward "6.1 already showed this is safe" as if it still applied unconditionally.
- One transaction; one `AuditLog` row (create), a before/after pair (correct).

### 6.2 The eligibility-and-assignment function the monthly job will call

A pure function of a student's full `StudentStatusChange` history, the student's `StudentPlanAssignment` history, the branch (`academyId`), and a target coverage month M with its generation date G(M) = the 1st of M in the branch's timezone — answering exactly what the (not-yet-built) monthly job needs. No separate "trusted from" input (section 4: "no history row strictly before G(M)" already means undecidable, on its own). No `now()` anywhere: this reads only committed history, so calling it for the same month twice, on different real dates, gives the same answer (3.1).

```
eligibleAndAssigned(statusHistory, assignments, academyId, month):
  status := the latest statusHistory row with effectiveOn < G(month), ordered by (effectiveOn, sequence); if none: -> UNDECIDABLE
  if status !== ACTIVE: -> NOT_ELIGIBLE (create nothing; the corrected strict cutoff and worked examples, 3.3)
  assignment := the latest assignment row with effectiveMonth <= month; if none, or planId is null: -> NO_ASSIGNMENT
  if assignment.plan's branch !== academyId: -> NO_ASSIGNMENT
  -> ELIGIBLE, with assignment.planId
```

The status cutoff is **strict** (`<`, not `<=`) for the reason worked through in 3.3: a status change effective on or after the 1st of `month` must never affect `month` itself, only the one after it. The assignment cutoff stays `<=` deliberately — it is a different kind of fact. `StudentPlanAssignment.effectiveMonth` already has month granularity with its own uniqueness constraint (`@@unique([studentId, effectiveYear, effectiveMonth])`, PR 2A), so at most one assignment row can ever apply to a given month; there is no same-period tie to guard against the way there is for a calendar-date status change, and no reason to exclude an assignment that took effect in `month` itself from applying to `month`.

`assignment.plan's branch !== academyId` is currently unreachable in practice (5.4: nothing changes a student's branch, ever), kept as a defensive check with no live path to exercise it today — matching PR 3's own precedent of an invariant the database or a check enforces even though nothing yet violates it. **A code comment at this exact line says so and points back to 5.4**, so if a transfer feature is ever added, whoever adds it finds the place that needs to change, not a silent wrong answer.

This is the same shape as PR 1's `priceFor`/`latestEffective` (already proven, already reused three times now — 2A's configuration versions, PR 4a's ledger writers, and 3.2's same-day status ordering above): "the latest version on or before the target," with an explicit "nothing yet" result rather than a guess, and — because it takes `month` as an explicit argument and reads nothing resembling a clock — the exact same answer whether it is asked on G(month) itself or years later during a recovery run (3.1). **Written and unit-tested as a pure function in this phase**, but **not called from anywhere** — same isolation discipline as PR 4a: no job, no caller, registered in `scripts/pending-callers.ts` for the monthly-job PR.

## 7. Tests and PR shape

- **Real-database tests, atomicity:** each of the five existing status actions writes its `StudentStatusChange` row in the same transaction as the status update (a forced mid-transaction failure rolls back both); `pauseStudent`/`resumeStudent` likewise; each new action's precondition refuses and writes nothing from every wrong starting status (`PENDING`/`ARCHIVED`/`INACTIVE` for pause, everything but `INACTIVE` for resume).
- **Resume's obligation-creation rule (3.4):** documentation only in this PR, not implemented, no tests here — `resumeStudent`'s own tests (above) cover only its status/history/audit write. 3.4's `dueOn`/`graceDeadline`/dedup rules are the payment-write integration PR's specification and get their tests there.
- **Same-day ordering (3.2):** two `StudentStatusChange` rows for one student with the identical `effectiveOn` are ordered by `sequence`, never by `createdAt`; a dedicated test asserts `sequence` is assigned as `MAX(sequence)+1` under the student lock and that `@@unique([studentId, sequence])` rejects a forced duplicate; a real two-connection concurrency test — two of `pauseStudent`/`resumeStudent`/`archiveStudent`/`restoreStudent` fired at the same student at once (the `pg_stat_activity`-polling pattern from PR 4a, not a wall-clock guess, given how variable this database's round-trip time already proved to be there) — exactly one succeeds under the lock, the loser's precondition correctly refuses against the now-current status, the winner's `sequence` reflects true commit order regardless of each transaction's own `createdAt`, and the final status column always agrees with the latest history row. **First-row atomicity:** `createStudent` and `signup` each insert their student row and its `sequence = 1` `StudentStatusChange` row in one transaction with no student-row lock taken; a forced mid-transaction failure rolls back both, leaving neither a student nor an orphaned history row.
- **Baseline:** run against a mix of `PENDING`/`ACTIVE`/`ARCHIVED` existing students; a second run touches nothing already captured; a student who gains a real `EVENT` row between two runs is correctly skipped by the second; a concurrency test — baseline and a real first-ever action (say `archiveStudent`) racing for the same never-touched student — produces exactly one first row for that student, never two, never neither.
- **Assignment:** tenant/branch validation (forged/foreign ids), package-plan refusal, past-month refusal, duplicate-month refusal; the correction's revision-token stale-edit detection and its atomic before/after audit row (mirroring PR 3's own tests exactly); current and past assignments refuse correction; a concurrent obligation-creation race is not needed here — no writer that exists today can reference a future assignment (6.1) — but a test still asserts a **current** month's assignment cannot be corrected even the instant it turns from future to current.
- **Eligibility function:** table-driven unit tests over the four outcomes (`UNDECIDABLE`, `NOT_ELIGIBLE`, `NO_ASSIGNMENT`, `ELIGIBLE`); every worked example in 3.3 as its own case (pause on the 1st still bills that month; pause on the 25th, same result; pause-then-resume same month nets to no effect; same-day pause-and-resume broken by `sequence`, both orderings); the strict-`<` boundary itself (a status change dated exactly `G(month)` must not affect `month`, only `month + 1`); and same-result-regardless-of-when-asked (calling it for October in October and again in December returns identically), mutation-checked. 6.2 itself has no resume-specific branch and needs none (3.4's obligation write happens directly in `resumeStudent`, never through this function), so no resume case belongs in this suite.
- **Structural:** the eligibility function (6.2) has no caller, verified the same way as PR 4a's writers (`tests/unit/dues-ledger-not-exposed.test.ts`'s pattern extended, or a sibling test). That test's existing assertion — nothing outside `src/lib/dues/ledger/` imports the ledger — needs **no change** for this PR; `resumeStudent` is not an importer.
- One focused PR; schema change is additive only (`StudentStatusChange`, `StudentPlanAssignment`'s writer — no new settings field, per section 4; no change to existing tables); CI normal, no retriggering; no deploy, no activation, no ledger caller exposed.
