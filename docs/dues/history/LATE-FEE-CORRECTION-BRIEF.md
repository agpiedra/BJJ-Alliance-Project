# Brief: correcting a fee wrongly assessed before an on-time payment was recorded

Status: **brief only, nothing implemented.** Written 2026-09-28 from main `ed8bd2e` (through the late-fee-assessment PR #72, merged). Every claim below was checked directly against that commit's actual code — file:line references throughout. **Revised 2026-09-28, corrected after review, approved for implementation with these corrections:** the brief overclaimed what "verification" means here — `lateFeeApplies` checks timeliness against the stored grace deadline *assuming the claimed `receivedOn` is true*; it cannot and does not verify that the payment actually happened on that date (no bank integration, no uploads — the date is owner-confirmed, taken on the owner's word, exactly like every other `receivedOn` this ledger already accepts). Likewise `expectedRevision` detects a stale view, not factual accuracy. §1 and §4 are corrected accordingly. The DB's `DuesLateFee_removal_marker_complete` constraint guarantees the fee row's own metadata is complete — it says nothing about whether an `AuditLog` row exists; that is a separate, writer-level guarantee, not a free consequence of the CHECK constraint, and §4 is corrected to stop conflating the two. §5's two open questions are now resolved: owner-only, reusing the ordinary `maxBackdateDays` (itself still an explicit, no-default parameter — D4 stays pending, unchanged), and an explicit submission with a required reason is sufficient confirmation — no extra checkbox. §2 adds the exact rollback mechanism a typed settlement refusal requires, and explicitly preserves oldest-first validation rather than bypassing it for a single-obligation correction. Previous version kept as `LATE-FEE-CORRECTION-BRIEF-before-precision-correction.md`.

**The example this brief is built around, exactly as given:** a student paid the full tuition on November 5 (on or before the grace deadline — on time). Staff didn't record it until November 6, by which point assessment had already run and created a `DuesLateFee` row. `recordDuesPayment` refuses this submission with `feeAlreadyAssessed` (`record-payment.ts:179`, unchanged, already documented as deliberate — "because removing it is undecided policy," and this brief is what finally decides it, narrowly). Because `recordDuesPayment` validates before writing, that refusal creates **nothing** — no `DuesPayment`, no `DuesSettlement`, no audit row. There is no existing settlement to undo here; this is a payment that was never successfully recorded, blocked by a fee that was never actually owed.

## 0. What already exists, verified — this phase corrects a narrow gap, not a new subsystem

- **The actual received date already has exactly one home**: `DuesPayment.receivedOn`, a required, caller-supplied `CalendarDate`, immutable once the row is created. This phase invents no second date field — the corrected payment's `receivedOn` is the same field every payment already has.
- **"On time" already has exactly one definition, used everywhere**: `lateFeeApplies(receivedOn, graceDeadline)` (`src/lib/dues/settlement.ts:37-39`) — inclusive grace deadline, already the sole authority `recordDuesPayment` and `assessLateFeeInTx` both use. This phase must not add a second, possibly-divergent notion of "on time" for corrections specifically.
- **The removal marker is already schema-complete and DB-enforced**, unreachable today only because nothing writes it: `DuesLateFee.removedAt`/`removalKind` (`WAIVED`/`VOIDED`)/`removedById`/`removalReason`, guarded by `DuesLateFee_removal_marker_complete` (verified in the migration): all four fields null, or all four set **and `removalReason` non-blank after trimming** — enforced by Postgres itself, not by application code remembering to check. A correction writer gets "always give a real reason" for free; it does not need to invent that requirement.
- **The revision-token stale-edit pattern already exists and is directly reusable**: `versionRevision(fields)` (`src/lib/dues/config-input.ts:76-82`) is a generic, model-agnostic fingerprint function — already used by `correctAssignment` (D25's pattern) for exactly this purpose. This phase reuses it verbatim; it does not need its own bespoke fingerprint.
- **`recordDuesPayment`'s existing behavior once a fee is voided already works — verified by reading its own logic, not assumed**: `asTerms`'s `lateFeeMinor` is already `0` whenever `removed` is true (`record-payment.ts:159` before this PR's refactor; the same fact now lives in `assessLateFeeInTx`'s fresh re-read); its `feeAlreadyAssessed` check (`:179`) only fires when a fee exists **and is not removed**. Once a fee is voided, a plain, ordinary, **unmodified** call to `recordDuesPayment` would already succeed and settle at the tuition-only amount. The only genuinely new problem this phase solves is doing the void and the settlement **together, atomically** — not inventing new settlement logic.

## 1. How the actual received date is recorded, and what "verified" honestly means here

**Corrected: `receivedOn` is owner-confirmed, not independently verified.** There is no bank integration, no receipt upload, no external source of truth this system checks the claimed date against — exactly like every other `receivedOn` `recordDuesPayment` already accepts on an owner's word, this phase builds no new proof mechanism and none is in scope.

What actually gets checked, once, under a lock, before anything is written:

```
check: lateFeeApplies(claimedReceivedOn, obligation.graceDeadline) === false
```

This verifies **timeliness given the claim** — *if* `claimedReceivedOn` is true, would it have been on time against the obligation's own stored grace deadline? It does not, and cannot, verify that the payment actually happened on that date; that fact rests entirely on the owner's own attestation, exactly as it already does for every ordinary payment recorded through `recordDuesPayment`. If the check fails — the claimed date, taken at face value, would itself be late — the action refuses (e.g. `notOnTime`) and **voids nothing**. This is the literal, honest enforcement of the confirmed rule: **only a claimed on-time payment date — consistent with the stored grace deadline — justifies removing a wrongly assessed fee.** The same `lateFeeApplies` function already used by `recordDuesPayment` and `assessLateFeeInTx` is reused here unchanged; this phase adds no second, competing definition of "on time," and no fact-checking machinery beyond what already exists for ordinary payments.

The `receivedOn` that passes this check is not a separate, throwaway value — it **is** the `receivedOn` the resulting `DuesPayment` row is created with (§2). Recording and checking are the same date, checked once, not two dates that could drift apart.

## 2. How an owner resolves the fee and records the full settlement atomically

**One writer, one transaction, composing two existing pieces rather than inventing new settlement logic — the same "narrow transaction-aware extraction" lesson already applied three times this session (`lockStudent`, `createMonthlyObligationInTx`, `assessLateFeeInTx`), now a fourth:**

1. `recordDuesPayment`'s existing validate-then-write body needs the same extraction those three already got: a `recordDuesPaymentInTx(tx, args, deps)` taking an already-open `tx` instead of opening its own, with the public `recordDuesPayment` becoming a thin wrapper exactly like `createMonthlyObligation`'s. Verified requirement, not optional: without this, the correction writer would have to nest a `prisma.$transaction` inside its own — the exact composition mistake already found and reverted once this session (resume/`createMonthlyObligationInTx`) — or fall back to two separate transactions, which is not what "atomically" means here (§5 explains why the gap between two transactions is a real, if narrow, problem, not a theoretical one).
2. The correction writer itself, one transaction:
   ```
   check context.organizationRole === "ADMIN" — refuse (notFound) otherwise; owner-only, not inferred from any roster gate
   lockStudent (same lock recordDuesPayment/assessLateFeeInTx already take)
   lock/re-read the named DuesLateFee row; refuse (stale) if expectedRevision doesn't match its current state — detects a stale VIEW,
     not a claim about factual accuracy (D25's exact pattern, versionRevision reused verbatim)
   refuse (notFound) if it's already removed — voiding is a one-time marker, not a re-appliable action
   re-read its obligation's graceDeadline
   check lateFeeApplies(receivedOn, graceDeadline) === false — refuse (notOnTime) otherwise, voiding nothing (§1: a consistency
     check against the claim, not proof the claim is true)
   mark the fee removalKind: VOIDED, removedAt: now, removedById: owner, removalReason: (required, non-blank)
   write its own AuditLog row for the void (before: the fee's prior null state, after: the void) — the writer's OWN
     responsibility, not something the DB's removal-marker CHECK constraint provides on its own (§4)
   call recordDuesPaymentInTx(tx, { ...the same payment payload, obligationIds: [this one obligation's id], maxBackdateDays }, deps)
     — the SAME transaction, no nesting, oldest-first and every other existing validation fully intact (§2.3)
   if that call returns any typed refusal (ok: false) — wrong amount, an older unpaid obligation still outstanding, too-old or
     future receivedOn, already settled, or anything else recordDuesPaymentInTx already refuses for — throw a tagged error
     carrying that exact refusal; do not return it directly from inside the transaction callback. Prisma only rolls back a
     transaction whose callback throws — a callback that returns normally, even with a "refusal" value, commits. The outer
     function catches that specific tagged error AFTER prisma.$transaction has rolled everything back (the void included) and
     only then returns the original typed refusal to the caller — never before rollback, never bypassing it.
   ```
   **Never commit a void without its matching full settlement.** A failure anywhere — the fee check, the payment validation, the settlement write, even the audit-log insert itself — rolls back **everything**, including the void: there is no state where a fee is voided but no payment exists, or a payment exists against a fee that was never actually voided.
3. **Scope boundary, deliberate, and not a shortcut around existing protection**: this phase corrects exactly the one obligation whose fee is being voided — matching the example given (one obligation, one wrongly-assessed fee). It does **not** bypass `recordDuesPaymentInTx`'s existing oldest-first validation to do this: the correction still calls it with `obligationIds: [this one obligation]`, exactly like an ordinary payment would, and if an older, still-outstanding obligation exists for the same student, the existing `notOldestFirst` refusal fires exactly as it already does today — rolled back per the mechanism above, voiding nothing. A multi-obligation settlement that happens to include one wrongly-fee'd obligation among several is a real but separate scenario this phase does not need to solve to fix the given case.

## 3. VOIDED (incorrectly assessed) vs WAIVED (valid fee forgiven) — two different questions, only one answered here

- **VOIDED** answers a question of **fact, taken on the owner's word**: given the receivedOn date the owner attests to, was this fee ever actually owed? §1's `lateFeeApplies` check enforces that consistency mechanically — it does not, and this phase does not attempt to, independently confirm the underlying fact. Voiding is not a favor to the student; it is the system recording that, given what the owner has attested, the fee should never have existed. This is the **only** action this phase builds.
- **WAIVED** answers a question of **policy**: the fee was genuinely, correctly assessed — the payment really was late, or there is no on-time payment at all — and an owner chooses to forgive it anyway, for reasons this system has no way to verify (goodwill, a hardship exception, a negotiated correction unrelated to timing). **This phase does not build a waiver writer.** Building one means deciding real policy this brief has not been asked to decide (does a waiver need its own justification category, does it require a different permission level than a void, does it interact with reporting differently) — exactly the kind of policy invention the confirmed rule says not to do. `WAIVED` stays schema-ready and structurally unreachable, precisely as it is today, until a separate phase deliberately decides it.
- **Explicitly not inferred from this phase**: no refund policy, no reversal policy. This correction never touches an *existing* settlement or payment (§0 — there isn't one yet in the scenario this solves) and never authorizes undoing one. Reversal (`DuesPayment.reversedAt`/`DuesSettlement.reversedAt`) remains exactly as pending as the late-fee-assessment brief already left it — nothing here decides it, nothing here assumes an answer to it.

## 4. Audit history, retries, and concurrency with assessment/payment recording

- **Two separate guarantees, corrected from an earlier draft that conflated them.** The DB-level `DuesLateFee_removal_marker_complete` constraint guarantees the **fee row's own** removal metadata is complete — `removalReason` non-blank, all four fields set together or none at all — enforced by Postgres regardless of application code. It guarantees nothing about whether an `AuditLog` row exists; that is a **separate, writer-level responsibility**. This phase's writer must itself insert the void's `AuditLog` row inside the same transaction as the fee update — atomic because both are in one transaction the writer controls, not because the CHECK constraint provides it for free. `recordDuesPaymentInTx`'s own existing audit-writing for the settlement is reused unchanged for the payment side.
- **Retries are naturally safe, by composition of guarantees that already exist**: `DuesLateFee`'s removal marker is one-time (a second void attempt on an already-voided row is refused, `notFound`-shaped, not a silent no-op that could re-void or double-audit); `recordDuesPaymentInTx` inherits `recordDuesPayment`'s existing replay safety (`alreadySettled` on a repeat). A retried correction request either fully re-applies from scratch (if the first attempt never committed) or is cleanly refused as already-done (if it did) — no new idempotency mechanism needed.
- **Concurrency with a live assessment run or an ordinary payment attempt is closed the same way every other race in this ledger has been closed this session**: `lockStudent`, first, before any obligation/fee/settlement data is touched. A concurrent `assessLateFeesForStudent` run for the same student, or a concurrent ordinary `recordDuesPayment` call, is strictly serialized against this correction by that same lock — whichever acquires it first fully determines what the other sees, the same property already proven for every prior race in this feature area.
- **The stale-edit case, concretely**: an owner opens the fee-correction view, sees the fee's current state, but before they submit, something else changes it — the same fee is corrected (or somehow removed) by a second owner, or an unrelated process. `expectedRevision` (D25's pattern, reused) catches this: the correction refuses (`stale`) rather than silently acting on a view that's no longer current. **Corrected: this proves the view wasn't stale — it proves nothing about whether the owner's claimed `receivedOn` is factually accurate** (§1). The two checks answer different questions and neither substitutes for the other.

## 5. Owner decisions — resolved

- **Owner-only.** `context.organizationRole === "ADMIN"` checked inside the writer itself (not deferred entirely to whatever eventually calls it) — the same "trust nothing from the caller" discipline `createMonthlyObligationInTx`/`assessLateFeeInTx` already apply to scope and activation, extended here to role, since this is the first writer in this feature area for which role is a first-class policy requirement rather than a request-layer concern alone.
- **Backdating limit: reuse the ordinary payment limit, no separate allowance.** `maxBackdateDays` is passed straight through to `recordDuesPaymentInTx` unchanged — a correction is validated exactly like an ordinary late-submitted-but-on-time payment would be, nothing more permissive. It remains, as it already is for `recordDuesPayment`, a **required, explicit parameter with no production default** — D4 itself stays exactly as pending as before; this phase does not resolve the numeric limit, only confirms the correction reuses whatever `recordDuesPayment` already requires.
- **Confirmation: an explicit submission with a required reason is sufficient — no additional checkbox.** The revision token (proves the view is current) plus the DB-enforced non-blank reason (proves *something* was articulated) together are the confirmation this phase builds. No separate "are you sure" gate.
- **Not reopened, still pending exactly as before**: D4's numeric value, D5 (who may call `recordDuesPayment` at all — this phase's writer additionally requires `ADMIN` specifically, a narrower, resolved question for *this* action only), reversal policy, waiver policy, refund policy.

## 6. Tests, planning-level

Real-database, all required:
- The exact example: assessed Nov 6 for a Nov 5 on-time payment, corrected successfully, obligation settled with no fee attached, `feeId: null` on the settlement.
- **Every refusal-after-provisional-void case, each proving the void itself is rolled back — fee, payment, settlement and audit state all exactly as before the attempt**: wrong tender amount; an older, still-unpaid obligation outstanding for the same student (oldest-first preserved, not bypassed); a `receivedOn` too old for `maxBackdateDays` or in the future; the target obligation already settled by the time the correction runs.
- A claimed date that is not on time against the stored grace deadline (`notOnTime`), voiding nothing.
- A non-`ADMIN` context refused.
- A stale `expectedRevision` refused; an already-voided fee refused on a second attempt.
- A forced audit-insert failure rolls back everything, including the void and any settlement writes already made in the same transaction.
- Concurrent assessment vs. correction, ordinary payment vs. correction, and two concurrent corrections for the same fee — all serialized correctly on the student lock, real two-connection concurrency, not wall-clock timing.
- `recordDuesPaymentInTx`'s extraction proven behavior-preserving against `recordDuesPayment`'s full existing suite, unmodified — validation, authorization boundaries, and activation checks all intact, the same proof used for every prior extraction this session.
- Direct-helper boundary tests: call the correction's own transaction-aware core directly (bypassing whatever thin wrapper exists), confirming it enforces role, scope, and activation itself rather than trusting a caller that skipped them — the same requirement the monthly-generation PR's review already established for this codebase's other extracted helpers.
