# Brief: purchasing a multi-month package

Status: **brief only, nothing implemented.** Written 2026-09-29 from main `5c51759` (through the monthly-prepayment PR #76, merged). **Corrected 2026-09-29** after review: the prior draft (a) failed to bind the purchase's start month to an explicit, caller-supplied selection — the exact retry-unsafe pattern PR #76's own approval already corrected for prepayment, re-introduced here by oversight; (b) missed that `settleReceipt` accepting a shorter prefix means its bare success is not proof the package was paid for; (c) proposed avoiding `recordDuesPaymentInTx` entirely rather than the narrower, correct fix of extending its settlement core; (d) made a factually wrong claim that `assessLateFeeInTx` would crash on a package obligation, and overstated a structural fact into a false technical necessity. All four are corrected below, verified directly against the actual code. Previous version kept as `PACKAGE-PURCHASE-BRIEF-before-atomic-receipt-correction.md`. **Confirmed package policies are unchanged, not reopened.**

## 0. Confirmed policies, restated exactly, not reopened

Reuse branch-specific, versioned Manage Plans; full upfront payment at the quoted package price; consecutive calendar-month coverage beginning at the first uncovered month; no overlapping coverage, partial payments, credit balance, unpaid package, or package late fee; existing outstanding debt settled oldest first; explicit purchase, no automatic renewal; pause/departure does not extend coverage; refunds and coverage release remain separate, unresolved work.

## 1. What already exists, verified

- **`PaymentPlanTerms` already supports a quoted whole-package price, no new field needed**: `priceAmount` (`schema.prisma:1171`) is documented on the column itself as *"the price of the whole offer (not per month)"* — already correct for `monthsCovered >= 2`. No schema change needed for Manage Plans reuse.
- **`DuesObligation`'s DB-enforced shape makes "no package late fee" unrepresentable, not merely a convention to remember**: `DuesObligation_shape_by_type` (`migration.sql:243-248`) requires, for `type = 'PACKAGE'`: `monthsCovered >= 2`, and `dueOn`, `graceDeadline`, `lateFeeAmount`, `policyVersionId` **all NULL**. The database refuses any other shape.
- **Coverage non-overlap is already fully enforced by the existing, generic `DuesCoverage` uniqueness**: `(studentId, year, month)` (`schema.prisma:1361`, not type-scoped) — a package's N coverage rows collide with this exact constraint the same way an ordinary `MONTHLY` obligation's single row would. `DuesObligation_student_month_monthly_key` (`migration.sql:277`), by contrast, is explicitly `WHERE "type" = 'MONTHLY'` — it gives packages no obligation-level protection of their own, so every coverage row must be created inside the same transaction as the obligation itself, before anything else can claim those months.
- **Reversal already refuses a payment touching a package obligation, for free, with zero code changes**: `reverse-payment.ts:101`'s existing `unsupportedObligationType` check (`type !== "MONTHLY"`) already covers `type: "PACKAGE"`. No change to `reverse-payment.ts` is needed for this phase.
- **`createMonthlyObligation`'s own `inapplicable` refusal already keeps `monthsCovered > 1` terms out of the ordinary monthly path** (`create-monthly-obligation.ts:87`), so package terms are already inert everywhere except a dedicated package writer.

## 2. Corrected factual claims from the prior draft

- **`assessLateFeeInTx` does not crash on a package obligation — verified directly, the prior claim was wrong.** Read in full (`record-payment.ts:68-107`): its own query filters `type: "MONTHLY"` in the `WHERE` clause itself (`:80`), and its refusal condition explicitly includes `obligation.graceDeadline === null` (`:83`) — both independent of, and in addition to, `recordDuesPaymentInTx`'s own outer `type: "MONTHLY"` filter (`:259-261`) that would exclude a package id from ever reaching this function's obligation-id loop in the first place. Either guard alone already refuses cleanly (`{ ok: false, error: "notFound" }`); nothing here reads a null `graceDeadline` unguarded. The prior draft's "real crash, not a graceful refusal" claim is retracted.
- **A package obligation not referencing `DuesPolicyVersion` does not mean `maxPrepaidMonths` cannot be read and applied to it — these are different facts, and the prior draft conflated them.** Reading the branch's current effective `maxPrepaidMonths` value (a plain `tx.duesPolicyVersion.findMany(...)` query, exactly as `prepayMonthlyObligations` already does) and using that number to bound a package purchase's *final covered month* requires no foreign key from the package obligation to that row at all — the check would simply be applied during purchase validation, the same way it already is for prepayment, with nothing stored differently on the resulting obligation. **Whether this check should exist is a genuine owner decision (§7); it is not foreclosed by anything structural, and the prior draft was wrong to suggest otherwise.**

## 3. Bind the purchase to explicit selections — corrected, matching PR #76's own established retry-safety discipline

**The prior draft's design computed the purchase's own start month internally (`resolve firstUncovered... require the package's months starting there`) rather than requiring the caller to name it and validating that name — the exact retry-unsafe shape the user's own approval already corrected for `prepayMonthlyObligations` (brief §7 there), reintroduced here by oversight. Corrected:**

The writer's arguments must include, explicitly, from the caller: **the student, the specific package terms/version id, the requested start month, and any existing-debt obligation ids to combine in the same receipt.** Duration is derived from the selected terms' own `monthsCovered` — never separately supplied, since a package's length is fixed by which terms it is. Under the branch/student locks, this writer:

```
resolve firstUncovered for this student (the same search prepay-monthly.ts already has — export it, or an identical one)
refuse (coverageGap) unless requestedStartMonth === firstUncovered — NEVER substitute the computed value for what was
  requested; a mismatch is refused, not silently corrected to "the actual next available month"
```

**An identical retry must not purchase a different, later span.** Because the start month is validated against the caller's own explicit selection rather than freshly computed and used, a retried identical request (same terms id, same requested start) that finds its target months already covered by the first attempt's own commit hits the existing `DuesCoverage`-uniqueness-backed pre-check (§1, §5) and refuses cleanly — it can never silently reach for "the next available span" instead.

## 4. Full settlement of the entire purchase — `settleReceipt`'s own success is not sufficient, corrected

**A real gap in the prior draft's design, caught by review, not previously identified: `settleReceipt` accepts any valid k-prefix of its item list, including one shorter than the whole list.** If the combined item list is `[debt1, ..., debtN, packageItem]` (package appended last, §6) and a receipt happens to equal the running total through `debtN` alone, `settleReceipt` returns `{ ok: true, settledIds: [debt1..debtN] }` — a **legitimate, successful** result that does **not** include the package. Treating `settleReceipt`'s bare `ok: true` as proof the whole purchase succeeded would silently leave the package obligation and its coverage rows standing, entirely unpaid — a direct violation of the confirmed "no unpaid package" policy, and exactly the state this feature must never produce even transiently.

**Corrected requirement**: after `settleReceipt` returns `ok: true`, this writer must explicitly verify `settledIds` includes **every** id it required — every named existing-debt obligation id **and** the package's own newly created obligation id. If any required id is missing from `settledIds` (meaning the tendered amount matched a shorter prefix than the full purchase), refuse the whole transaction and **roll back everything already provisionally written** — the package obligation, every one of its coverage rows, and any other write made so far in this transaction — using the same throw-tagged-error-then-convert-after-rollback mechanism every writer since `correctLateFeeAndSettle` has used. A receipt that pays off only the existing debt is not a partial success to accept; it is a refusal of the whole request, with zero net effect.

## 5. One atomic receipt path — reusing `recordDuesPaymentInTx`'s settlement core, not duplicating it, and not avoiding it

**Corrected: the prior draft's recommendation to avoid composing `recordDuesPaymentInTx` at all was an overcorrection.** §2 shows the actual obstacle is narrower than "cannot be used at all": `recordDuesPaymentInTx`'s outer obligation query is `type`-scoped (`:259-261`) and its per-obligation loop unconditionally assesses a fee (`:328-344`) — both of which are wrong for a package item specifically, not wrong in general, and both refuse cleanly rather than crash if reached with a package id (§2) — but "refuses cleanly" is still the wrong behavior here: a package settling in the same receipt as current debt must actually succeed, not be treated as `notFound`.

**Recommended fix, a narrow internal extraction — not duplicated financial logic, and not a second payment path:**

- The generic prefix of `recordDuesPaymentInTx` (activation, `validatePaymentInput` — already its own separate, shared, exported helper, `:238` — student/scope checks, amount parsing, the student lock, the branch lookup, `today`/backdating validation) is **already type-agnostic** and already effectively reusable as-is; no extraction is needed for this part.
- The type-specific remainder — building the ordered item list, running `settleReceipt`, and then writing one `DuesSettlement` per settled item, calling `assessLateFeeInTx` **only** for items whose obligation is `type: "MONTHLY"` and skipping it entirely for the package item (`lateFeeId: null`, no fee lookup, no fee row, ever) — is the part that needs to become a shared, general core rather than the `MONTHLY`-only body it is today. Recommendation: extract this into its own transaction-aware function that accepts a pre-resolved, already-ordered list of settlement items (each carrying its own type) instead of internally querying `type: "MONTHLY"` obligations itself; `recordDuesPaymentInTx` becomes a thin wrapper that builds the `MONTHLY`-only list it already builds today and calls this shared core; the package writer builds its own combined list (current debt, resolved the identical way `recordDuesPaymentInTx` already resolves it, plus the package item appended last, per §6) and calls the same shared core.
- This produces **one `DuesPayment`, one transaction, covering both the current-debt portion and the package** — never two separate payments for the two portions, matching the confirmed "existing outstanding debt settled oldest first, [with the package,] in one receipt" policy exactly.
- **Preserved, unmodified, by construction of this design**: received-date/backdating validation (`validatePaymentInput`, reused verbatim), currency-mismatch and amount-unsupported rules (`settleReceipt`/`outstandingItems`, reused verbatim), removed-fee handling for the current-debt portion (`asTerms`'s existing `removed` check, reused verbatim for every `MONTHLY` item, untouched), and the throw-and-convert rollback guarantee (extended to cover the package's own provisional writes per §4).
- The exact shape of this extraction (function name, argument shape) is left for implementation to finalize — the brief's job is identifying that a narrow, shared core is the right fix, not a second, duplicated settlement path, and not avoidance of `recordDuesPaymentInTx`'s existing logic altogether.

## 6. Concurrency, price/version evidence — unchanged from the prior draft, still verified sound

Same branch → student → terms lock order every writer in this ledger already takes; a package needs no `lockPolicyShared` for its own price resolution (it references no policy row), and needs `lockAssignmentShared` only if resolving which package plan a student is buying requires reading `StudentPlanAssignment` the same way monthly purchases do (confirm during implementation). Concurrent monthly generation, concurrent second purchases, concurrent assignment/configuration corrections all close the same way PR #76 already established for the equivalent races. Price/terms evidence: the package obligation snapshots `terms.priceAmount`/`currency` and the specific `planTermsId` relied upon, immutable afterward — the entire evidence trail, since the price is quoted for the whole span, not per month.

## 7. Owner decisions — APPROVED

1. **Owner-only (`context.organizationRole === "ADMIN"`), enforced inside the writer itself** — not inferred from prepayment's own approval, asked and confirmed on its own terms, the same "trust nothing from the caller" discipline every owner-only writer in this ledger already applies to its own role check.
2. **The existing prepayment horizon (`maxPrepaidMonths`) also bounds a package's final covered month.** Resolved from the policy version effective at recording time (`purchaseInstant`, captured once, after the relevant locks — the exact same discipline PR #76 established for prepayment's own limit), never from `receivedOn`. Unset (`null`) means unavailable, exactly as for prepayment. Lowering the limit later never touches a package's already-purchased coverage — the same forward-only gating principle already confirmed for prepayment.
3. **Package terms effective at recording time, refused if the requested terms/version is no longer applicable — never silently repriced.** The caller names the specific terms id it quoted; if that id is no longer the currently-effective one for the package plan (superseded by a correction since the quote was shown), refuse (`staleTerms` or equivalent) rather than substituting whatever is effective now. **No separate quote-expiration subsystem** — this reuses the existing "resolve the currently-effective version, refuse if the named one has been superseded" pattern `createMonthlyObligationInTx`'s own `staleVersion` check already establishes (`create-monthly-obligation.ts:88`), not a new mechanism.
4. **`firstUncovered`'s search floor is the current branch-local calendar month, not `currentMonth + 1`.** A package may legitimately start immediately — an ordinary way to pay, not exclusively a pay-ahead tool. Existing obligations and coverage (whether paid or unpaid, `MONTHLY`, `PACKAGE`, or any other origin) reserve their months regardless — the search still finds the true first *uncovered* month, never replacing or overlapping an existing obligation, paid or not. Earlier unpaid debt remains payable oldest first through the ordinary current-debt portion of the same receipt (§6) — this writer still never invents a historical/enrollment charge to fill a gap that predates its own found starting point; it only ever creates the ONE package obligation for the span it resolves, nothing to backfill anything before it.

## 9. Tests, planning-level

Real-database, all required, same genuine-concurrency discipline as every prior phase:

- A package purchase creates one `DuesObligation` (`type: PACKAGE`) and exactly `monthsCovered` `DuesCoverage` rows, one `DuesPayment`, one settlement for the package (`lateFeeId: null`), combined atomically with any named current debt in the SAME receipt.
- **§4's exact scenario**: a receipt whose amount matches only the current-debt portion's running total (a valid `settleReceipt` prefix that excludes the package) is refused in full — zero writes, including the package obligation and every one of its coverage rows rolled back, not left standing unpaid.
- **§3's exact scenario**: a request naming a `requestedStartMonth` that does not equal the true `firstUncovered` is refused (`coverageGap`), never silently redirected to the actual next-available span; an identical retry after a first successful purchase refuses cleanly via existing-coverage detection, never reaching for a later span.
- Duplicate/retry, overlap refused, mid-transaction rollback (forced failure and settlement-incompleteness both), price/terms evidence frozen regardless of a later terms correction — as before.
- Reversal already refuses via the existing `unsupportedObligationType` check — a regression test confirming this holds, not a new mechanism.
- Concurrent monthly generation, concurrent second purchase, concurrent assignment/configuration correction: genuine overlap, not sequential.
- Ordinary `recordDuesPayment` (all-`MONTHLY` receipts) behavior fully unaffected by whatever extraction §5 produces — its own full existing suite passes unmodified.
