## 0. What already exists, verified — reversal is smaller than it looks, because most of the "after" behavior is already correct by construction

- **The schema is already reversal-ready, structurally identical to `DuesLateFee`'s removal marker**: `DuesPayment` and `DuesSettlement` each have `reversedAt`/`reversedById`/`reversalReason`, guarded by `DuesPayment_reversal_marker_complete`/`DuesSettlement_reversal_marker_complete` — all-or-nothing, **non-blank reason enforced by Postgres itself** (verified in the migration, identical shape to the late-fee constraint this session already relied on). A `dues_set_once_marker` trigger (`DuesPayment_marker_once`, `DuesSettlement_marker_once`) makes the reversal marker **permanently one-time at the database level** — not just an application convention. This gives "owners only, with a required reason and permanent audit history" most of its enforcement for free.
- **Every existing reader already treats a reversed settlement as if it doesn't exist — verified, not assumed, and scoped precisely to what this actually establishes.** `recordDuesPayment`'s own obligation query (`record-payment.ts:260`, unchanged since PR 4a): `settlements: { where: { reversedAt: null }, select: { id: true } }`, then `open = all.filter(o => o.settlements.length === 0)`. `assessLateFeeInTx`'s own settlement lookup (`:100` in the merged `record-payment.ts`): `duesSettlement.findFirst({ where: { ..., reversedAt: null }, ... })`. **This means "existing monthly obligations become unpaid again" is not new logic reversal has to implement — it is the existing, already-tested read path's behavior the moment `reversedAt` is set.** Reversal's job is almost entirely about the *write* (who may do it, atomically, with what's reversed together) — not the read-side consequence, which already exists. **Corrected: this establishes only what currently, mechanically happens to the *obligation's* paid/unpaid status. It is not, and must not be read as, an answer to or endorsement of either fee-policy question in §2 — those are about `DuesLateFee`, a table this existing behavior says nothing about.**
- **`DuesCoverage` cannot be touched by reversal even by accident — structurally, not by discipline.** Its only creation site in the entire codebase is `create-monthly-obligation.ts:120`, inside `createMonthlyObligationInTx`, atomic with the *obligation's* creation — never with a payment or settlement. Reversal, which only ever reads/writes `DuesPayment`/`DuesSettlement`, has no code path that reaches `DuesCoverage` at all. "Obligations and coverage remain intact" is therefore already guaranteed by what tables reversal touches, not something its logic has to specifically protect.
- **A `DuesLateFee` row can only ever reference a `MONTHLY` obligation — a real database constraint, not an application convention.** `DuesLateFee_only_monthly` (verified in the migration): `CHECK ("obligationType" = 'MONTHLY')`. This is what makes the detection mechanism in §2.2 exact rather than a guess.
- **Corrected: `recordDuesPayment`'s `type: "MONTHLY"` filter (`record-payment.ts:80,260`) is a fact about today's one existing writer, not a database guarantee `DuesSettlement` enforces.** Checked directly: `DuesSettlement`'s own foreign key to `DuesObligation` (`DuesSettlement_organizationId_obligationId_studentId_fkey`) carries no type restriction at all — nothing in the schema stops a *future* writer from creating a settlement against a non-`MONTHLY` obligation. `type: "MONTHLY"` therefore cannot be cited as proof that a settlement was never created through some future prepayment path — see §2.3 for the actual, robust reason nothing reaches reversal outside its intended scope today, and for how the writer must verify its own scope at runtime rather than assume it.

## 1. Confirmed rules restated as design constraints, not reopened

- **What the database enforces, precisely — and no more.** `DuesPayment_reversal_marker_complete`/`DuesSettlement_reversal_marker_complete` guarantee the marker's four fields are set all-or-nothing, with a non-blank reason. `dues_set_once_marker` guarantees, once set, it can never be changed again. That is the *entire* scope of what Postgres enforces here: a **complete, one-time** marker. It says nothing about *who* may set it and nothing about whether an `AuditLog` row accompanies it.
- **What only the application enforces — corrected from an earlier draft that blurred this line.** **Owner authorization** (`context.organizationRole === "ADMIN"`) is entirely the writer's own responsibility, checked by the writer itself before it ever reaches the transaction — the database has no concept of role here and would accept a reversal from any caller with database access. **Transactional `AuditLog` creation** is equally the writer's own responsibility: nothing in the schema requires an audit row to accompany a reversal, or ties the two together — the writer must itself insert the `AuditLog` row inside the same transaction as the marker update, the same distinction the late-fee-correction brief already had to draw for the fee's removal marker.
- **Reverse the payment and all its active settlements atomically.** A single payment can settle several obligations together (`recordDuesPayment`'s own doc comment: "several months can be settled together") — reversal takes a `paymentId`, not a `settlementId`, finds every one of its currently-active (unreversed) settlements, and marks the payment and all of them reversed in one transaction. There is no partial reversal of a multi-obligation payment in this design; reversing the payment reverses everything it settled.
- **No amount fields to reconcile.** `DuesSettlement` has no amount columns at all ("one payment settling one obligation, in full" — already the schema's own shape); reversal doesn't need to compute or undo a partial amount, only flip the marker on the rows that exist.
- **Refunds remain separate** — reversal records that a payment is no longer considered received against these obligations; it says nothing about whether money moves back to anyone, and this phase does not build that.

## 2. Two separate policy decisions, with concrete examples — both approved 2026-09-28

**2.1 Decision A: reversing a payment that settled tuition plus a valid, never-voided late fee.**

*Example:* a student's settlement covers USD 100 tuition plus a genuinely, correctly-assessed USD 20 late fee — one payment of USD 120, one settlement, `lateFeeId` pointing at a fee that was never touched by any correction. The payment bounces; an owner reverses it. **The question:** after reversing this mistaken payment, should both the USD 100 tuition and the USD 20 fee remain owed?

**Approved 2026-09-28: yes — retain the existing fee, create no second one.** Mechanically, this needs no new logic: the `DuesLateFee` row was never touched by anything in §1's scope, so it's already exactly where it should be (unremoved, still referencing the same obligation); reversing the settlement makes the obligation unsettled again (§0), and a later payment naturally re-includes the same still-active fee (verified: `asTerms`/`feeOwed` in `record-payment.ts` depend only on `removedAt`, never on settlement history). Implementation proves the full chain (settle-with-fee → reverse → re-settle → exactly one fee row) with a real test, not this reasoning alone.

**2.2 Decision B: reversing a payment whose recording also voided an assessed fee (`correctLateFeeAndSettle`, PR #73).**

*Example:* a fee was assessed, then correctly `VOIDED` because the payment turned out to be genuinely on time — the void and the settlement were created together, atomically, in one transaction (PR #73's whole design). The payment itself now proves mistaken (it bounced, or was entered in error) and needs reversing. **The question:** what should happen to the fee's now-permanent `VOIDED` state?

**Approved 2026-09-28, as a temporary restriction: refuse this specific reversal outright — no writes at all — until fee-restoration policy is decided.** Concretely: the writer checks, for the obligation behind each settlement it's asked to reverse, whether a `DuesLateFee` row exists with `removalKind: "VOIDED"` (a plain read, no new schema). If one exists on *any* affected obligation, refuse the *whole* reversal (e.g. `voidedFeeBlocksReversal`) and write nothing. **This deliberately does not silently preserve the forgiveness (leaving the fee voided forever with no path back) and does not invent an un-void mechanism on the spot** — it surfaces the case explicitly, to a human, rather than picking either outcome by default.

**Corrected: this is a conservative restriction keyed on the obligation's current fee state, not a claim about causation.** The check is "does this obligation currently have a voided fee" — full stop. It does not establish, assert, or need to prove that *the specific payment being reversed* is the one that caused that void (even though today, given `correctLateFeeAndSettle`'s design, that happens to be the only way a voided fee can exist alongside a settlement). No provenance field links a settlement to "the void it caused," and this PR adds none — the restriction is deliberately broader and simpler than trying to prove a causal link, exactly because proving that link would require new schema this phase does not add.

Everything **not** matching this condition (Decision A's case, and any obligation with no fee at all) proceeds normally — this restriction does not block the rest of reversal's scope, only this one specific, detectable case.

**2.3 Supported scope: packages and prepayment — corrected reasoning, and how the writer verifies its own scope at runtime**

**What's actually true, verified, and robust to how a future feature gets built** (§0's correction): no writer today creates an obligation for a future coverage month, of *any* type — `createMonthlyObligation`'s `futureMonth` refusal is the only obligation-creation path that exists, and it refuses unconditionally. That is the real reason nothing resembling a prepayment settlement can exist yet — not `type: "MONTHLY"`, which prepayment would almost certainly still use (a future coverage month, not a different type). `type: "PACKAGE"` obligations are separately confirmed absent (grepped the codebase, no writer creates one) — packages and prepayment are two different future features, and this reasoning doesn't conflate them.

**Because `DuesSettlement`'s own foreign key carries no type restriction (§0), the reversal writer cannot rely on history holding forever — it must check its own supported scope explicitly, at runtime, on the specific row it's asked to reverse.** Concretely: before reversing, re-read the obligation each settlement being reversed belongs to, and refuse (e.g. `unsupportedObligationType`) if its `type` is not `MONTHLY` — the one type this writer is built and tested against. This is not presented as proof that nothing else can ever exist; it is the writer's own defensive boundary, the same "trust nothing, verify explicitly" discipline already applied to scope and activation elsewhere in this ledger. Today, this check has no live path to trigger it (nothing can produce a non-`MONTHLY` settlement) — a documented, unreachable backstop, the same pattern already used for `eligibility.ts`'s branch-scope check and `classifyRecordPaymentError`'s kept-but-dead `DuesLateFee` branch. The day a prepayment or package writer is built, this is exactly the line that needs revisiting, and it will already be there, refusing safely, rather than silently mishandling a case nobody designed for.

## 3. Explicitly not inferred, per the confirmed constraint

No fee restoration policy, no fee cancellation policy, no refund policy — §2.2's recommendation is a proposal for how to *avoid* deciding those prematurely, not a decision about them. This brief identifies the unsupported/unresolved cases above; it does not silently pick an answer for any of them by building a writer that only handles the cases with settled answers and hopes the rest don't come up.

## 4. Scope for this phase

**Corrected: this no longer waits entirely on §2.2.** §2.2's recommended refusal is itself the implementation for that specific, narrow case — it does not block the rest of reversal's scope, which covers Decision A (§2.1) and every ordinary, no-fee case without needing either recommendation approved first. Only the *outcome* for the one detectable overlap (a voided fee behind the settlement being reversed) depends on §2.2's answer; until then, the writer refuses that one case explicitly rather than guessing.

1. A writer (name TBD, e.g. `reversePayment`) — owner-only (`context.organizationRole === "ADMIN"`, checked by the writer itself, an application responsibility per §1), one transaction, `lockStudent` first (matching every other ledger writer this session), taking a `paymentId` and a required, non-blank reason (refused cleanly by the writer before ever reaching the DB's own constraint, the same discipline already applied to `removalReason`).
2. **Re-reads everything under the lock, trusting nothing from before it** — the payment, its currently-active (unreversed) settlements, and each settlement's obligation. Refuses if the payment is already reversed (one-time, matching the DB's own set-once trigger), not found, or out of tenant scope.
3. **Verifies its own supported scope explicitly** (§2.3): each settlement's obligation must be `type: "MONTHLY"` — refuse (`unsupportedObligationType`) otherwise, a documented, currently-unreachable backstop, not a live case.
4. **Checks for §2.2's approved restriction**: if *any* affected obligation has a `DuesLateFee` row with `removalKind: "VOIDED"`, refuse the whole reversal (`voidedFeeBlocksReversal`) and write nothing — a restriction on the obligation's current fee state, not a claim that this payment caused the void (§2.2's correction) — until fee-restoration policy is decided.
5. Otherwise, marks the payment and every one of its active settlements reversed, in the same transaction, with the one shared reason and its own `AuditLog` row(s) (one per row changed, or one covering all of them — a small design choice for whoever implements this, not decided here). Explicitly does **not** touch `DuesLateFee`, `DuesObligation`, or `DuesCoverage` beyond the read in step 4 — by §0's verified facts, it doesn't need to.
6. **Any refusal, or any failure at any point, leaves everything exactly as it was** — one transaction, nothing partially applied; a mid-transaction failure rolls back the marker update and any audit rows together, the same guarantee every writer this session has been held to.
7. No caller wired anywhere — not a route, not a server action, not a scheduler entry. Gated by the same `LedgerActivation` default (inactive), checked by the writer itself. Registered in `scripts/pending-callers.ts`.
8. Tests, real-database: Decision A's full chain (settle-with-fee → reverse → re-settle, §2.1); Decision B's refusal (a voided fee blocks reversal cleanly, no writes, until §2.2 is answered); the `unsupportedObligationType` backstop (forced against a non-`MONTHLY` obligation, since nothing today can trigger it naturally); a multi-obligation payment reversed atomically (all settlements flip together, none left half-reversed); an already-reversed payment refused; owner-only enforced; a forced mid-transaction failure leaves everything unchanged; concurrent reversal vs. a live payment/assessment/correction attempt for the same student serialized on the student lock; the existing `recordDuesPayment`/`assessLateFeeInTx`/`correctLateFeeAndSettle` suites passing unmodified.
