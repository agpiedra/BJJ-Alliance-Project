# Brief: late-fee assessment (the job that proactively marks an overdue obligation fee-owed)

Status: **brief only, nothing implemented.** Written 2026-09-28 from main `2e61f37` (through the monthly-generation PR #71, merged, both commits). Every claim below was checked directly against that commit's actual code — file:line references throughout. **Revised 2026-09-28, corrected after review, approved for implementation with these corrections:** §5's claim that PR 2B's coverage-reversal precedent extends "by identical reasoning" to late fees is withdrawn — reversal policy for fees is separate and pending, not decided here. The activation-prerequisite framing for `feeAlreadyAssessed` is strengthened from a footnote to an explicit readiness-checklist item. §2/§6 correct `settledOn` to specifically mean the active settlement's `DuesPayment.receivedOn` (never `DuesSettlement.createdAt`/`DuesPayment.recordedAt`), excluding reversed settlements. §6's helper design is corrected to re-read obligation/settlement/fee state itself, fresh, under the lock — never trusting a caller-supplied snapshot — and adds an explicit never-commit-an-incomplete-settlement guard plus P2002-constraint disambiguation. §8 updated to match, with the exact required race tests named. Previous version kept as `LATE-FEE-ASSESSMENT-BRIEF-before-safety-correction.md`.

## 0. What already exists, verified, that this phase builds on — more than expected

`recordDuesPayment` (`src/lib/dues/ledger/record-payment.ts`) already creates a `DuesLateFee` row today — but only as a side effect of a *late payment being recorded*, never proactively. This phase's whole job is to make that same fact assessable **before** anyone tries to pay, using the writer's own already-correct logic, extracted rather than reinvented:

- **The pure decision is already built and unit-tested** (`src/lib/dues/settlement.ts`, PR 1): `lateFeeApplies(receivedOn, graceDeadline)` (`:37-39`, inclusive grace deadline), `feeAssessableFrom(graceDeadline)` (`:42-44`, the day after), and — the one most directly reusable here — `lateFeeToAssessMinor(obligation, asOf)` (`:60-64`): "nothing through the grace deadline, then one fixed fee, however late, however often asked — it never grows," already handling a zero fee and an already-settled obligation correctly by construction.
- **The write pattern is already built, inline, inside `recordDuesPayment`** (`:202-225`): for each obligation a fee is owed on, check for an existing `DuesLateFee` row first (reuse it, never recreate — `:209-213`), skip entirely when `lateFeeMinor` is 0 (`:180`, `feeOwed` is false), and otherwise `tx.duesLateFee.create(...)` plus one `AuditLog` row, inside the same transaction that holds `lockStudent` (`:125`). This phase's writer is a **narrow transaction-aware extraction of this exact block** — the same pattern already used twice (`lockStudent` out of the ledger, `createMonthlyObligationInTx` out of `createMonthlyObligation`) — not new logic.
- **`DuesLateFee` has no amount column at all** — the fee amount is the snapshot already on `DuesObligation.lateFeeAmount` (`:1315`, "the fee this obligation incurs if it is late... zero allowed," captured at obligation creation). A `DuesLateFee` row is a **marker** (existence, `assessableFrom`, removal state), not a separate money record — "one snapshotted fee" is already literally true of the schema.
- **`DuesLateFee.obligationId` is unconditionally unique at the database level** (`DuesLateFee_obligationId_key`, verified in the migration, not a partial index) — at most one fee row ever exists per obligation, active or removed, enforced by Postgres regardless of what any writer does, backstopping the student lock exactly the way `DuesSettlement`'s and `StudentPlanAssignment`'s own unique indexes already backstop their locks.
- **No waiver/void writer exists anywhere in this codebase** — grepped for `removalKind`/`removedAt` usage outside the schema and the `record-payment.ts` read path: nothing writes it. `removedAt`/`removalKind`/`removedById`/`removalReason` are schema-ready but structurally unreachable today.
- **`AuditLog.actorId` is nullable with an existing, unrelated precedent for exactly this case** (`:1530-1535`, verified verbatim): *"null for an automated system action - 'do not invent a human actor' applies to the audit trail too."* This phase's runner is the first writer in the dues area to actually be that automated actor — reuse this existing convention, don't invent a new one.

## 1. One snapshotted fee per overdue monthly obligation, after its inclusive grace deadline

Already the schema's own shape (0 above). The runner's job, per still-open `MONTHLY` obligation: compute `lateFeeToAssessMinor({ ...obligation snapshot, settledOn: null }, today)`; if it returns > 0 and no `DuesLateFee` row exists yet for it, create one — `assessableFrom` computed by `feeAssessableFrom(graceDeadline)`, never from "today" (this is what makes recovery honest, §4). If a fee row already exists (created earlier by this same runner, or by a late payment through `recordDuesPayment`), do nothing — reuse, never recreate, exactly `recordDuesPayment`'s own existing behavior (`:209-213`).

## 2. Existing settlements, waived/voided fees, and zero-fee obligations — three reasons to do nothing, already distinguishable

- **Already settled** (an active, unreversed `DuesSettlement` exists for the obligation): `lateFeeToAssessMinor` already handles this correctly when given the real `settledOn` — settled on or before the deadline means no fee was ever owed, no matter how late the runner happens to ask. **`settledOn` is specifically the settlement's `DuesPayment.receivedOn` — the calendar date money was received — never `DuesSettlement.createdAt` or `DuesPayment.recordedAt` (both are row-creation instants, not the received date `lateFeeApplies`/`lateFeeToAssessMinor` are defined against, `settlement.ts:37,56-58`).** A **reversed** settlement (`DuesSettlement.reversedAt` set) does not count as an active payment and must be excluded from this lookup entirely — the obligation is unsettled for this purpose, `settledOn` is `null`, exactly `recordDuesPayment`'s own existing `settlements: { where: { reversedAt: null } }` filter (`:137`).
- **Waived or voided** (`DuesLateFee.removedAt` set): the row already exists — the "existing fee row, reuse it" branch above already refuses to touch it. The runner never re-creates a fee over an existing row regardless of its removal state; this is a `find`, not an `upsert`.
- **Zero fee** (`DuesObligation.lateFeeAmount` null or 0): `lateFeeToAssessMinor` naturally returns 0 — no row is created, exactly matching `recordDuesPayment`'s existing `feeOwed` check (`:180`). Nothing new to build; reuse the same pure function and the same "0 means skip" reading of it.

## 3. Concurrent assessment and payment recording, using consistent locks

The runner takes `lockStudent` (`FOR UPDATE`) before reading a student's obligations and fees, in one transaction, exactly the lock `recordDuesPayment` already takes for the same tables (`:125`) — whichever of the two (a concurrent payment or a concurrent assessment run) acquires it first fully determines what the other sees, the same serializability property already established for the monthly-generation/`assignPlan` races. The unique index on `obligationId` (0 above) is the backstop if a race somehow still reaches two create attempts: the loser gets a constraint violation, caught and treated as "already assessed," never a crash — mirroring `recordDuesPayment`'s own existing `P2002` → `alreadySettled` catch (`:253-255`) as the pattern to follow, not a new decision.

## 4. Safe repeated runs and missed-run recovery

- **Repeated runs are naturally idempotent**: the unique index means a second run for an already-assessed obligation finds the existing row and does nothing — no flag needed, no "already ran today" bookkeeping, the same "zero rows / one row, nothing in between" idempotency shape baseline (`src/lib/students/baseline-action.ts`) already established for a different table.
- **A missed run (the job doesn't run for days) recovers correctly, but `assessedAt` and `assessableFrom` mean different things — worth stating precisely, since the monthly-generation brief made an analogous overclaim before correction.** `assessableFrom` is computed purely from the obligation's own `graceDeadline` (`feeAssessableFrom`, no clock) — identical whether assessed on time or three weeks late, exactly like `dueOn`/`graceDeadline` on the obligation itself. `assessedAt` (`@default(now())`, `:1375`) is honestly the real creation instant — it **should** differ between an on-time run and a recovered one, and that is correct, not a bug: it is when the fact was recorded, not when the fee became owed. Recovery here means "the same fee gets assessed, dated by when it became owed, not by when someone noticed" — not "every timestamp is identical no matter when this runs."

## 5. Backdated-payment and reversal cases, stated explicitly, no new policy invented

- **`feeAlreadyAssessed` becomes a live, reachable refusal once this ships — it is not a new decision, but its consequence changes, and resolving it is now an activation prerequisite, not a footnote.** `recordDuesPayment` already refuses a payment whose `receivedOn` is on time when an unremoved fee already exists (`:179`, "because removing it is undecided policy" — already decided, already documented). Today that path is nearly unreachable, since the only way a fee exists today is a *prior late payment itself* succeeding. Once this phase ships, a fee can exist **before** any payment attempt — so a genuinely on-time payment recorded *after* assessment already ran will actually hit this refusal in ordinary use, not just in theory. **This phase preserves that refusal exactly as it is — it does not silently waive or void a fee, and does not build a waiver/void writer.** Documented here as a required item for the activation readiness checklist: before billing activation, this scenario needs an approved resolution workflow (most plausibly a waiver/void writer, §0 — none exists today), or staff will have a real, unresolvable case on day one of live billing. Not blocking *this* PR; blocking *activation*.
- **Reversal policy for late fees remains pending — not decided by this brief, and not inferable from the coverage precedent.** Reversal doesn't exist as a writer yet at all (confirmed — grepped, nothing sets `DuesPayment.reversedAt`/`DuesSettlement.reversedAt` anywhere), so this phase does not build it and takes no position on it. An earlier draft of this brief claimed that PR 2B's "reversal never auto-releases `DuesCoverage`" decision extends "by identical reasoning" to late fees. **That claim is withdrawn — it does not follow, and this brief must not prescribe reversal behavior for fees.** Coverage-overlap protection and a late-fee's survival across a reversal are two separate policies; deciding one says nothing about the other. Whoever designs the reversal action decides this fresh, on its own terms, when that phase is actually scoped.

## 6. Reuse of existing fee calculations and payment-writer behavior

1. **Extract, don't reimplement**, the fee-creation block already inside `recordDuesPayment` (`:202-225`) into a small transaction-aware function — but **corrected from an earlier sketch of this brief**: the helper does not accept a caller-supplied `obligation`/`settledOn` snapshot as trusted input (a caller could pass something read before the lock, or simply wrong). It takes only an identifier and re-reads everything itself, fresh, under the lock:
   ```
   assessLateFeeInTx(tx, { context, obligationId }, deps):
     activation check (repeated here, not only at whatever calls this)
     re-read the DuesObligation by id, scoped to organizationId — notFound if missing
     enforce inTenantScope(context, obligation.academyId) — notFound if out of scope
     re-read its active (reversedAt: null) DuesSettlement, joined to DuesPayment for receivedOn — this IS settledOn, never
       DuesSettlement.createdAt or DuesPayment.recordedAt (§2's correction)
     re-read any existing DuesLateFee row for this obligation
     if one exists: return { ok: true, feeId: that row's id } — untouched, whatever its removal state
     compute lateFeeToAssessMinor(obligation snapshot with the re-read settledOn, today) — if 0, return { ok: true, feeId: null }
     otherwise create the DuesLateFee row + its audit row (actorId: null for an automated caller, a real one for a manual trigger
       if this is ever exposed to one) and return { ok: true, feeId: new row's id }
   ```
   `recordDuesPayment` is refactored to call this same function, per obligation it's settling, instead of its current inline duplicate — one implementation, two callers, the `createMonthlyObligationInTx` precedent, corrected this time to not trust a snapshot the way that extraction's `student` parameter still does (a difference worth naming, not silently copying forward).
2. **`recordDuesPayment` must never commit an incomplete settlement because of what this helper returns.** Its own validation phase already decided, per obligation, whether a fee is owed (`feeOwed`, `:180`) before any write begins — VALIDATE FIRST, THEN WRITE, unchanged. When its write phase then calls `assessLateFeeInTx` for real, the returned `feeId` must agree with what validation already expected (present when `feeOwed` was true, `null` when it was false) — under this phase's own lock discipline this can never actually disagree, but if it ever does, `recordDuesPayment` must treat that as an internal failure and abort the whole transaction, never proceed to create a settlement whose `lateFeeId` doesn't match reality. This is an assertion to add, not a new refusal code for a real user-facing case.
3. **`P2002` is not one thing.** `recordDuesPayment`'s existing catch (`:253-255`) treats every `P2002` as the settlement race and reports `alreadySettled` — correct today, because `DuesSettlement`'s partial unique index is the only unique constraint this writer could ever collide on. Once it also creates `DuesLateFee` rows through a path that can race a concurrent assessment run, a `P2002` can come from *either* constraint. Inspect the error's own constraint target (Postgres reports which one) before choosing a response: a settlement collision is still `alreadySettled`; a late-fee collision means the row was created between this transaction's read and its write — treat it as already assessed and re-read the row rather than fail; anything else is a genuinely unexpected error and must be re-thrown, never silently absorbed into either label.
4. The new runner reuses `lateFeeToAssessMinor`/`feeAssessableFrom` directly from `settlement.ts` — no new fee arithmetic anywhere in this phase.

## 7. A server-only runner, inactive and without a route, action or scheduler

Same isolation discipline as `generateMonthlyObligationForStudent`, not a new decision: a plain exported function (e.g. `src/lib/dues/late-fee-assessment.ts`), no route, no server action, no `vercel.json` entry, gated by the same `LedgerActivation` (inactive by default) — checked inside the extracted transaction-aware helper itself, not only at whatever entry point calls it, per the exact lesson the monthly-generation PR's review already applied. No caller; registered in `scripts/pending-callers.ts`; the ledger no-caller guard updated to name this one new file explicitly, the same precise, non-broadened pattern already used twice.

## 8. Scope for this phase, given the above

1. `assessLateFeeInTx(tx, { context, obligationId }, deps)` — re-reads obligation, active settlement (with its payment's `receivedOn`), and existing fee state itself under the lock (§6); trusts nothing supplied by its caller; enforces activation and `inTenantScope` itself.
2. `recordDuesPayment` refactored to call it, per settled obligation, in place of its inline block — behavior-preserving, proven by its own unmodified test suite; the P2002-disambiguation fix (§6.3) applied to its existing catch.
3. A new runner, per student per branch: one transaction (`lockStudent` first, matching `recordDuesPayment`'s own lock), reads open `MONTHLY` obligations, and for each one calls `assessLateFeeInTx` by id.
4. No caller wired anywhere. No change to `LedgerActivation`'s default. No change to `settlement.ts`'s pure functions. No reversal behavior implemented or prescribed for fees (§5).
5. Tests, real-database:
   - Zero-fee obligation skipped; already-settled-on-time obligation skipped even when asked very late (using the payment's `receivedOn`, not a row-creation timestamp); already-settled-late-with-existing-fee reused, not duplicated; waived/voided fee never re-created; reversed settlement treated as unsettled, not as an active on-time payment.
   - **Both concurrency orders of an on-time payment recorded after grace has passed, explicitly**: (a) payment's transaction wins the lock first → settles on time → assessment then sees the active on-time settlement and creates no fee; (b) assessment's transaction wins the lock first → creates a fee (nothing settled yet) → the payment then correctly returns `feeAlreadyAssessed` with zero payment-side writes (no `DuesPayment`, no `DuesSettlement`, no audit row) — proving the already-existing refusal still fires correctly once assessment can reach it in practice (§5).
   - A genuinely late payment (received after grace): fee created and settled together, as today.
   - Repeated assessment runs (idempotent) and two concurrent assessment runs for the same student (serialize on the lock, no duplicate fee, unique index as backstop).
   - The P2002-disambiguation itself: force a settlement-uniqueness collision and a late-fee-uniqueness collision separately, confirm each produces its own correct outcome, and confirm an unrelated `P2002` (or any other unexpected error) is re-thrown, not absorbed.
   - `recordDuesPayment`'s existing suite passes unmodified; structural no-caller guard naming the one new runner file.

**Explicitly not reopened:** D1 (CRC/USD conversion), D4 (backdating limit), D5 (who may call `recordDuesPayment`), D24/D25, packages, prepayment, refunds, resume-charge timing, reversal policy for fees (§5, pending, not this phase's to decide). **Activation prerequisite, not blocking this PR:** no waiver/void writer exists — `feeAlreadyAssessed` becomes a real, reachable refusal once this ships, preserved exactly as-is (never silently waived or voided), with no resolution path for staff until a waiver/void writer exists and billing activation must not proceed without one.
